## Module 1 — الهوية والصلاحيات (Dynamic RBAC)

> كموظف في الفريق، عايز أدخل بالإيميل وكلمة السر، علشان أوصل للنظام بصلاحيات دوري.

**الجداول** `users` · `roles` · `permissions` · `role_permissions` · `user_sessions`

**الـ Endpoints**
- [ ] `POST /api/v1/auth/login` · `logout` · `change-password`
- [ ] `GET /api/v1/auth/me`
- [ ] CRUD `/api/v1/roles` · `/api/v1/permissions` · `/api/v1/users`

**الواجهة** صفحة دخول · تحويل حسب الدور · مسارات محمية · شاشة إدارة الأدوار والصلاحيات

**معايير القبول**
- [ ] بيانات صحيحة ← تحويل لشاشة الدور الافتراضية
- [ ] 5 محاولات فاشلة ← الحساب بيتقفل وإيميل بيتبعت
- [ ] جلسة ساكنة 8 ساعات ← خروج تلقائي
- [ ] صلاحية اتشالت من دور ← نداء مباشر للـ API بيرجع **403**
- [ ] كلمة سر أقل من 8 حروف أو أرقام بس ← بترفض برسالة واضحة
- [ ] موظف معطّل ← "الحساب موقوف، من فضلك اتواصل مع الإدارة"
- [ ] الـ Super Admin مخفي من كل قوائم المستخدمين، لكل الأدوار
- [ ] الـ Manager مش بيقدر يعمل حساب Manager أو CEO أو Super Admin
- [ ] `Login As` للـ Super Admin بس وبيكتب audit entry دايمًا

🚀 **أول نقطة رفع — ارفع على السيرفر الحقيقي هنا، مش في الآخر.**

**الجداول** `customers` · `import_batches` · بالإضافة لـ **`SearchService`** بـ `PostgresSearchDriver` (ILIKE)

**الـ Endpoints** CRUD + `PATCH /:id/archive` · `PATCH /:id/assign` · `POST /import`

**الواجهة** قائمة مفلترة حسب الدور · فورم إضافة/تعديل · صفحة التفاصيل · أرشفة (فردية + تحديد الكل) · استيراد Excel · فلتر "عملاء الموظفين المعطّلين"

**معايير القبول**
- [ ] موظف المبيعات يشوف عملاءه بس · الـ Team Leader يشوف فريقه · الـ Manager يشوف الكل
- [ ] استيراد Excel ببيانات ناقصة ← السجل يتحفظ ومعلّم **"غير مكتمل"**، وله فلتر مخصص
- [ ] السجلات غير المكتملة **مستبعدة من التقارير المالية** لحد ما تتكمّل
- [ ] اسم شبيه بعميل موجود ← **تحذير أصفر**؛ الموظف هو اللي يقرر، مفيش منع
- [ ] عميل متأرشف يدويًا ← يشوفه الـ Manager والـ Team Leader بس
- [ ] تغيير مالك الحساب ← العميل وكل تاريخه بينتقلوا + audit entry
- [ ] **كل نداء بحث بيعدّي على `SearchService`** — مفيش استعلامات مباشرة

## Module 5 — الطلبات / الصفقات ⭐

> كـ Team Leader، عايز أدخّل طلبات العملاء وأوزّعها على الموظفين، علشان الشغل يمشي في المسار الصح.

**الجداول** `deals` · `deal_documents` · `deal_status_history` · محرك حالة العميل (`recompute_customer_status`)

**الـ Endpoints**
- [ ] CRUD `/api/v1/deals`
- [ ] `PATCH /api/v1/deals/:id/assign` · `/approve` · `/reject` · `/status`
- [ ] `POST /api/v1/deals/:id/documents`

**معايير القبول**
- [ ] عميل عنده صفقة شغالة + طلب جديد ← **صفقتين مستقلتين** بحالات منفصلة
- [ ] الصفقة توصل `Won` ← حالة العميل تبقى **"عميل"** تلقائيًا وبشكل دائم
- [ ] كل الصفقات `Lost` ← الحالة تبقى **"صفقة لم تكتمل"**
- [ ] طلب مدخّل من موظف ← يظهر للـ Team Leader كـ "في انتظار الموافقة" وميبقاش نشط لحد الموافقة
- [ ] طلب مرفوض ← سبب إجباري + شارة للموظف
- [ ] تغيير حالة ← سطر في الـ timeline بالحالة القديمة والجديدة ومين وإمتى
- [ ] أكواد الصفقات بالشكل `DL-2026-0001`

## Module 6 — عروض أسعار الموردين

> كموظف مبيعات، عايز أسجّل عرض سعر المورد وأرفق ملفه، علشان أستخدمه في بناء عرض العميل.

**الجداول** `supplier_quotations` (بـ `deal_id` **قابل للفراغ**) · `supplier_quotation_items`

**معايير القبول**
- [ ] عرض فيه منتج مش في الكتالوج ← المنتج بيتضاف تلقائيًا
- [ ] العرض بعد الحفظ يظهر في صفحة المورد تحت "العروض المرتبطة"
- [ ] عرض مش مربوط بصفقة ← بيتحفظ عادي ومتاح لأي صفقة
- [ ] رفع ملف ← النوع والحجم والـ **MIME الحقيقي** بيتفحصوا، والتخزين باسم UUID
- [ ] شاشة مشتركة — مش مقيّدة بالملكية

## Module 7 — عروض أسعار العملاء ⭐ (أصعب موديول)

> كموظف مبيعات، عايز أبني عرض سعر لعميلي باستخدام أسعار الموردين وهامش ربح، علشان أبعته بعد موافقة الـ Team Leader.

**الجداول** `quotations` · `quotation_items` · `quotation_additional_items` · `user_term_suggestions`

**الـ Endpoints**
- [ ] `POST /api/v1/quotations` · `GET /:id`
- [ ] `PATCH /:id/submit-for-approval`
- [ ] `POST /:id/new-version`
- [ ] `GET /api/v1/quotations?group_by=employee|customer`

**الواجهة** باني عرض السعر — موردين ديناميكيين بـ (+) لحد 10 · منتجات لكل مورد · حساب لحظي · معاينة تأكيد قبل الحفظ · SmartTermInput

**معايير القبول — أهم حاجة في المشروع كله**
- [ ] تكلفة 1000 وهامش 20% ← سعر البيع **1200** تلقائيًا
- [ ] هامش العرض 20% وهامش السطر 30% ← السطر بياخد **30%**
- [ ] موردين بعملات مختلفة ← التحويل بسعر الصرف الملتقط وقت الإنشاء، وعملة واحدة للعرض
- [ ] إجمالي 1234.67 جنيه ← الإجمالي النهائي **1235** و `rounding_diff` = **0.33**
- [ ] إجمالي 1234.678 دولار ← الإجمالي النهائي **1234.68** (وحدة التقريب 0.01)
- [ ] كمية أكبر من المسجّل عند المورد ← **تحذير أحمر داخل السطر**، مش منع
- [ ] منتج من غير سعر مسجّل ← **الحفظ ممنوع**
- [ ] سعر المورد اتغير بعد بناء العرض (`Draft`) ← تحذير + زرار "تحديث الأسعار"
- [ ] الموظف والـ Team Leader بيعدّلوا في نفس اللحظة ← **409 Conflict**

**قواعد الفلوس — مفيش استثناءات**
- [ ] `Decimal` في كل حتة؛ مفيش float بيلمس سعر
- [ ] كل الحسابات في الـ backend
- [ ] مفيش تقريب وسيط — الإجمالي النهائي بس
- [ ] تعديل سعر الصرف عمره ما يغيّر عرض موجود
- [ ] اختبارات وحدة لكل معادلة وحد تقريب وتحويل عملة وخصم وضريبة وبند إضافي

## Module 10 — رد العميل وأوامر الشراء

> كموظف مبيعات، عايز أسجّل رد العميل، علشان الصفقة تمشي في المسار الصح.

**الجداول** `purchase_orders` — `po_number` تلقائي + `customer_po_reference` نص حر + تاريخ + مرفق

**معايير القبول**
- [ ] `Partial` أو `Counter` ← نسخة كاملة بتتحفظ تلقائيًا والموظف يعدّل في النسخة الجديدة
- [ ] `Counter` أو `Rejected` ← **سبب إجباري** قبل قبول الحالة
- [ ] `Rejected` ← العرض يتأرشف · **العميل يفضل في القائمة** · الصفقة تبقى `Lost`
- [ ] `valid_until` عدّى من غير رد ← **`Expired`** تلقائيًا (J-01)
- [ ] البحث شغال على رقم أمر الشراء الداخلي وعلى رقم العميل
- [ ] كل نسخة محفوظة عبر `parent_id` + `version`

**الجداول** `visits` · `visit_areas`

**معايير القبول**
- [ ] فورم الزيارة فيه **تلات حقول إجبارية بالظبط**: اسم الشركة · الشخص المسؤول · النتيجة
- [ ] النت قطع أثناء الكتابة ← المسودة بتتحفظ محليًا وما بتضيعش
- [ ] نتيجة "ناجحة" مع طلب ← الطلب بيتوجّه تلقائيًا للـ Team Leader وبيتعلّم "تم"
- [ ] رفض ← سبب إجباري، بيغذّي تقرير الشركات الرافضة
- [ ] الـ VPN مفصول ← **رسالة واضحة ومحددة**، مش خطأ عام
- [ ] المشرف يشوف الزيارات والصفقات في نطاق `Out`، و**ما يشوفش أي صفقة بعد التسليم**
