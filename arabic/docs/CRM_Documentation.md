## 2. سجل القرارات

كل حاجة تانية في المستند ده قايمة على القرارات دي. **وأي تغيير مستقبلي بيتسجّل كقرار جديد هنا، مش كتعديل صامت للنص.**

### 2.1 الهيكل والتسعير

| # | القرار |
|---|---|
| D-01 | **الصفقة كيان مستقل** — مش حقل حالة على العميل. والعميل الواحد ممكن يكون عنده كذا صفقة متوازية |
| D-02 | **الطلب هو صفقة** — كيان واحد مش اتنين. وشاشة "طلبات العملاء" هي قائمة الصفقات |
| D-03 | هامش الربح بيتطبّق على **مستوى العرض ومستوى السطر** |
| D-04 | **سعر البيع = تكلفة المورد + الهامش** (بيتحسب تلقائيًا) |
| D-51 | **عرض سعر المورد كيان مستقل**، مربوط بصفقة اختياريًا (قابل لإعادة الاستخدام) |
| D-21 | **الأسعار مكانها عرض سعر المورد** — والكتالوج فيه بيانات وصفية بس |

### 3.12 قواعد بتعلو على المصفوفة

1. **الفرض بيحصل على مستوى الـ API** — إخفاء الزرار مش زي منع الإجراء.
2. **على مستوى الحقل:** تكلفة المورد وأسماء الموردين والهامش **عمرهم ما يكونوا موجودين في PDF العميل**، مهما كان مين اللي بيولّده.
3. **مفيش حذف نهائي** للعملاء ولا الصفقات ولا التقارير ولا الموردين — تعطيل أو أرشفة بس.
4. **سجلات audit إجبارية** لـ: تعديلات الضريبة · تعديلات الهامش · إعادة توزيع العميل · تغيير الدور · `Login As` · الاسترجاع من الأرشيف · تغيير سعر الصرف · تعطيل الحساب · الموافقة الذاتية.
5. **الصلاحيات موجودة في الداتابيز** — تغيير المصفوفة دي تغيير إعدادات، **مش رفع نسخة**.
6. **الـ Super Admin مخفي** — عمره ما يظهر في أي قائمة مستخدمين، لأي دور.
7. **الـ Manager مش بيقدر يعمل** حسابات Manager أو CEO أو Super Admin.

## 4. نموذج البيانات

### 4.1 خريطة الكيانات

```
العميل
   └── الصفقة (الطلب)                      ← D-01, D-02
         ├── مستندات الصفقة
         ├── عروض الأسعار (v1 → v2 → v3)   ← عروض العملاء ونسخها
         │     ├── بنود العرض
         │     └── البنود الإضافية
         ├── أمر الشراء (مرفق من العميل)

المورد ──► عرض سعر المورد                  ← كيان مستقل (D-51)
                    │
                    └── deal_id (اختياري — قابل للفراغ)
                    └── أسعاره بتغذّي بنود العرض
```

## 5. قواعد التسعير

> **أهم قسم في المستند ده.**

### 5.1 مستوى السطر (`quotation_items`)

```
unit_cost         = سعر وحدة المورد (بعملة المورد)
unit_cost_base    = unit_cost × fx_rate_at_time      ← تحويل لعملة العرض (D-09)
margin_percent    = هامش السطر؛ لو فاضي بيرث هامش العرض (D-03)
unit_price        = unit_cost_base × (1 + margin_percent / 100)   ← (D-04)
line_total        = unit_price × quantity
line_cost         = unit_cost_base × quantity
```

### 5.2 مستوى العرض

```
subtotal            = مجموع line_total
discount_amount     = subtotal × discount_percent / 100          ← (D-07)
net_amount          = subtotal − discount_amount
additional_total    = مجموع البنود الإضافية (توصيل / تركيب)

tax_base            = net_amount + additional_total    ⚠️ قرار مفتوح OD-01
tax_amount          = tax_base × tax_percent / 100
total_before_round  = tax_base + tax_amount

final_total         = round(total_before_round, وحدة العملة)   ← (D-06, D-52)
rounding_diff       = final_total − total_before_round         ← بيتخزن
```

### 5.3 وحدة التقريب لكل عملة (D-52)

| العملة | الوحدة الافتراضية |
|---|---|
| EGP | 1 جنيه |
| USD | 0.01 دولار |
| EUR | 0.01 يورو |

قابلة للتعديل من `إعدادات النظام ← العملات`. **والتقريب بيتطبّق على الإجمالي النهائي بس.**

### 5.4 حساب الربح

```
total_cost     = مجموع line_cost
gross_profit   = (net_amount + additional_total) − total_cost
margin_ratio   = gross_profit ÷ (net_amount + additional_total) × 100
```
> **الضريبة مش ربح** — بتتحصّل لحساب الدولة ومستبعدة من الربح.

### 5.5 بعد المشتريات

```
saving        = old_total_cost − new_total_cost
final_profit  = gross_profit + saving
saving_ratio  = saving ÷ old_total_cost × 100
```

### 5.6 قواعد إجبارية

- كل الحسابات بتشتغل في الـ **backend** — والواجهة بتعرض بس.
- **`Decimal` بس** — الـ Float ممنوع.
- كل مبلغ بيخزّن: `amount` · `currency` · `fx_rate_at_time` · `base_amount`.
- تغيير سعر الصرف **عمره ما يأثر** على عرض موجود.
- منتج أو سعر ناقص عند المورد ← **منع الحفظ**.
- الكمية المطلوبة أعلى من المسجّلة عند المورد ← **تحذير أحمر داخل السطر**.

- عند **`Partial`** أو **`Counter`** أو **`Returned`**، النظام بيحفظ نسخة كاملة والموظف بيعدّل في نسخة جديدة (D-08).
- مربوطة بـ `parent_id` + `version`؛ وكل النسخ بتفضل ظاهرة تحت "العروض السابقة" جوه الصفقة.
- **أسباب الرفض والتعديل إجبارية** قبل قبول تغيير الحالة.

### 6.4 دورة الموافقة

```
Draft ──إرسال──► Pending ──┬──موافقة──► Approved ──إرسال──► Sent
                            ├──تعديل + موافقة──► Approved
                            └──إرجاع بملاحظة──► Draft (v2)
```

- الـ Team Leader والـ Manager بيشاركوا **نفس الشاشة ونفس الصلاحية** (D-10).
- يقدروا يعدّلوا الضريبة أو الهامش أو أي حقل — **وكل تعديل بيتكتب في الـ audit**.
- **مفيش تصعيد تلقائي** (D-11) — شارة حمرا وعمود "أيام الانتظار".
- **قفل تفاؤلي** ← التعديل المتزامن بياخد **409 Conflict**.

### 6.5 الموافقة الذاتية (D-50)

الـ Team Leader (أو الـ Manager) يقدر يوافق على عرض بناه بنفسه، **بشرط الشفافية الكاملة**:

| المتطلب | التنفيذ |
|---|---|
| علامة على العرض | `is_self_approved = true` |
| شاشة الموافقات | شارة صفرا: **"موافقة ذاتية"** |
| سجل الـ audit | سطر نوعه `SELF_APPROVAL` — **مش موافقة عادية** |
| تقرير الأداء | عمود "الموافقات الذاتية" |
| لوحة الـ Manager | عدد الموافقات الذاتية في الفترة |

### 6.6 عروض الأسعار للـ Team Leader والـ Manager

مبدّل في الأعلى: **حسب الموظف · حسب الشركة · قائمة مسطحة**

بعدين التسليم ← إتمام التسليم ← تقرير المشتريات + تقرير الحسابات (PDF يدوي — D-23).

## 10. الحالات الحدّية

### 10.1 موظف معطّل عنده شغل مفتوح (D-34)

| البند | السلوك |
|---|---|
| الحسابات | **بتتعطّل مش بتتحذف** — `is_active = false` |
| العملاء والصفقات | بيفضلوا مربوطين بالموظف المعطّل |
| الوصول | الـ Team Leader والـ Manager بيفضل عندهم وصول كامل |
| إعادة التوزيع | الـ Team Leader بينقلهم وقت ما يحب (**مفيش نقل تلقائي**) |
| الدخول | ممنوع — "الحساب موقوف، من فضلك اتواصل مع الإدارة" |
| التقارير | تقاريره التاريخية بتفضل في السجل |

**مطلوب:** فلتر **"عملاء الموظفين المعطّلين"** في شاشة العملاء للـ Team Leader والـ Manager.

### 10.2 العملاء المكررين (D-35)
- عند الحفظ، النظام بيقارن الاسم بالسجلات الموجودة (**تطابق تقريبي** مع تطبيع الهمزة والتاء المربوطة وأشكال الياء).
- التشابه فوق الحد ← **تحذير أصفر** بقائمة العملاء المتشابهين.
- الموظف يقدر يكمّل، أو يفتح العميل الموجود بدل كده. **مفيش منع ومفيش دمج تلقائي.**
- 📌 دمج المكررين ← بعد الـ MVP.

### 10.3 تغيّر سعر المورد بعد بناء العرض (D-36)

| الحالة | السلوك |
|---|---|
| العرض في **`Draft` أو `Pending`** | بيحتفظ بسعره الأصلي + **تحذير أحمر**: "سعر المورد اتغيّر — راجع التسعير" |
| العرض **`Sent` أو بعدها** | **متأثرش خالص** — لقطة ثابتة |
| زرار "تحديث الأسعار" | في `Draft` بس — بيعيد الحساب وبيكتب سطر audit |

**ونفس المنطق بينطبق على** عرض مورد منتهي الصلاحية ← تحذير جنب اسم المورد وقت الاختيار.

### 10.4 منتج/مورد معطّل مستخدم في عرض مفتوح (D-37)

| الموقف | السلوك |
|---|---|
| العروض المفتوحة | المنتج **بيفضل شغال**؛ والحسابات ما بتتأثرش |
| التحذير | تحذير أصفر: "المنتج ده معطّل في الكتالوج" |
| العروض الجديدة | **بيتخفي** من قوائم الاختيار |
| البحث | بيظهر معلّم "معطّل" لو اتبحث عنه صراحةً |

### 10.5 حالات إضافية

| الحالة | القرار |
|---|---|
| عرض عدّى `valid_until` | **`Expired`** تلقائيًا — والموظف بيصدر واحد جديد أو بيسجّل `Rejected` بسبب "لا يوجد رد" |
| عميل بصفقتين متوازيتين | صفقتين مستقلتين بحالات وعروض منفصلة (D-01) |
| تعديلات متزامنة على عرض واحد | **409 Conflict** + "العرض ده اتغيّر، من فضلك حدّث الصفحة" |
| موردين بعملات مختلفة | التحويل بسعر الصرف الملتقط وقت الإنشاء؛ والعرض بيتصدر بعملة واحدة (D-09) |
| منتج من غير سعر مورد مسجّل | **الحفظ ممنوع** برسالة واضحة |
| كمية أعلى من المسجّل عند المورد | **تحذير أحمر** — مش منع |
| استيراد Excel ناقص | بيتعلّم "غير مكتمل" وله فلتر مخصص، و**مستبعد من التقارير المالية** لحد ما يتكمّل |

## 11. التقارير

### 11.1 المبادئ
- التقرير **لقطة ثابتة** — أرقامه وقت الإرسال، مع PDF متخزن.
- أغلب البيانات **بتتعبّى تلقائيًا**؛ والموظف بيراجع ويضيف ملاحظات ويرسل.
- **الدورات على مستوى النظام**، محسوبة من تاريخ الإطلاق (D-27).

### 11.2 الأنواع

| النوع | الكود | التوليد | صاحبه |
|---|---|---|---|
| تقرير صفقة | RPT-DL | يدوي | المبيعات · المشتريات · TL · Manager |
| يومي | RPT-DY | شبه تلقائي | كل الموظفين |
| أسبوعي | RPT-WK | تلقائي | كل الموظفين |
| نظرة شهرية | RPT-MN | تلقائي | النظام → Manager + CEO |
| حسابات | RPT-FN | يدوي | TL · Manager · المشتريات |
| أداء الموظفين | RPT-PF | يدوي | TL · Manager · المشرف الخارجي |
| زيارات | RPT-VS | يدوي / أسبوعي | المبيعات الخارجية · المشرف |
| مشتريات | RPT-PR | يدوي / شهري | المشتريات |

### 11.3 الحقول المشتركة
كود التقرير · العنوان · النوع · **النطاق الزمني (إجباري)** · صاحبه · تاريخ الإنشاء · تاريخ الإصدار · المستلمين (اختيار متعدد مفلتر بالصلاحية) · الحالة · **ملاحظات نص حر (لكل نوع)** · المرفقات.
الإجراءات: حفظ كمسودة · إرسال · تصدير PDF · تصدير Excel.

### 11.4 دورة الحياة
```
Draft → Submitted → Viewed → Acknowledged → Archived
                       ↘ Returned (سبب إجباري) → Draft (v2)
```
- بعد `Acknowledged` التقرير **للقراءة بس بشكل دائم، حتى لصاحبه**.
- والنسخة السابقة بتفضل متاحة للمقارنة.
- **مفيش حذف** — أرشفة تلقائية بعد 6 شهور، وبتفضل قابلة للعرض والتصدير.
- نفس النوع والفترة والموظف **مينفعش يترفعوا مرتين** — تحذير بيسأل: تعدّل الموجود ولا تعمل نسخة جديدة؟

### 11.5 التوقيت
- **اليومي:** الموعد من الإعدادات · ولو اتفوّت ← **`Missed`** + شارة للـ Team Leader.
- **الأسبوعي:** مسودة تلقائية · ولو ما اتوافقش عليه خلال 24 ساعة ← بيترفع معلّم **"غير مُراجَع"**، وبيظهر بشكل بارز.
- أيام الشغل **الأحد → الخميس** — والمواعيد بتتخطى الويكند.

### 18.3 بعد الـ MVP: مركز الإشعارات الكامل

القنوات: داخل التطبيق (افتراضي) · push (للميدان بس) · بريد (استثناء).
الأولويات: حرج (شريط) · عالي (toast + شارة) · عادي (شارة) · منخفض (قائمة بس).

**قواعد الشغل:**
- **التجميع افتراضيًا** — الإشعارات المتكررة بتتجمع في واحد بعدّاد.
- **ميزانية يومية** لكل مستخدم؛ والزيادة بتتجمع في ملخص آخر اليوم.
- **إخفاء تلقائي عند الإجراء** · **مفيش إشعارات تأكيد**.
- **تصعيد مرة واحدة** — مفيش سلالم تذكير.
- **الشارة قبل الإشعار** · **التحقق ≠ إشعار**.
- ساعات الهدوء للـ push بس · إزالة التكرار · إعادة المحاولة · **مفيش حذف**.
- **الموظف عمره ما يستقبل إشعار عن عميل مش بتاعه.**
