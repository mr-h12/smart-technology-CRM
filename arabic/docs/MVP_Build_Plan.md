## 2. الموديولات

> الترتيب مقصود — كل موديول معتمد على اللي قبله. الإعدادات والعملات والصلاحيات بييجوا **قبل** عروض الأسعار، علشان عروض الأسعار محتاجة التلاتة.

### Module 0 — الأساسات
**بنية تحتية — مفيش user story**

- هيكل المشروع (backend + frontend) · الاتصال بالداتابيز · أدوات الـ migration
- **طبقة i18n من أول يوم** — مفيش نصوص مكتوبة في الكود (عربي + إنجليزي)
- **نظام التصميم** + تخطيط RTL/LTR أساسي
- **طبقة تجريد التخزين** + جدول `files`
- **الـ audit log كطبقة شاملة** — بتشتغل تلقائيًا لكل موديول بعد كده
- **بنية الطوابير والمهام** — الأربع طوابير (`critical` · `pdf` · `reports` · `maintenance`)
- **بيانات أولية** — أدوار · صلاحيات · قطاعات · وحدات · عملات · مستخدمين للاختبار

✅ **الاختبارات:** التطبيق بيشتغل · الواجهة بتكلّم الـ backend · الداتابيز متصلة · تغيير اللغة بيقلب الاتجاه · مهمة تجريبية بتتنفذ من الطابور

### Module 1 — الهوية والصلاحيات (Dynamic RBAC)
**User story:** كموظف في الفريق، عايز أدخل بالإيميل وكلمة السر، علشان أوصل للنظام بصلاحيات دوري.

**الجداول:** `users` · `roles` · `permissions` · `role_permissions` · `user_sessions`

**نقاط الـ API:**
```
POST /api/v1/auth/login · logout · change-password
GET  /api/v1/auth/me
CRUD /api/v1/roles · /api/v1/permissions · /api/v1/users
```

**الواجهة:** صفحة دخول · تحويل حسب الدور · مسارات محمية · شاشة إدارة الأدوار والصلاحيات

**معايير القبول:**
- بيانات صحيحة ← تحويل لشاشة الدور الافتراضية
- 5 محاولات فاشلة ← الحساب بيتقفل وإيميل بيتبعت
- جلسة ساكنة 8 ساعات ← خروج تلقائي
- صلاحية اتشالت من دور ← لما المستخدم ينادي الـ API مباشرة ← **403**
- كلمة سر أقل من 8 حروف أو أرقام بس ← ترفض برسالة واضحة
- موظف معطّل ← "الحساب موقوف، من فضلك اتواصل مع الإدارة"

🚀 **أول نقطة رفع: ارفع على السيرفر الحقيقي هنا — مش في الآخر.**

---

### Module 2 — الإعدادات والقوائم المُدارة والعملات
**User story:** كمسؤول نظام، عايز أظبط بيانات الشركة والعملات والقوائم، علشان النظام يشتغل على بيانات الشركة الحقيقية.

**الجداول:** `settings` · `currencies` (+ وحدة التقريب) · `fx_rates` + التاريخ · `enum_lists` (قطاعات · وحدات · أنواع خدمات · شروط تسليم) · `system_limits` (حد الركود · موعد التقرير · SLA الموافقة · أقصى حجم ملف)

**معايير القبول:**
- تعديل سعر صرف ← السعر القديم يفضل في التاريخ + سطر audit إجباري
- قطاع جديد اتضاف في الإعدادات ← يظهر في فورم العميل **من غير رفع نسخة**
- تغيير وحدة تقريب عملة ← **العروض الجديدة بس** هي اللي بتتأثر

---

### Module 3 — العملاء
**User story:** كموظف مبيعات، عايز أضيف وأشوف عملائي المسندين ليّا، علشان أقدر أدير صفقاتي.

**الجداول:** `customers` · `import_batches`
**بالإضافة لـ `SearchService`** (تجريد البحث) — أول تنفيذ `PostgresSearchDriver` (ILIKE)

**نقاط الـ API:** CRUD + `PATCH /:id/archive` · `PATCH /:id/assign` · `POST /import`

**الواجهة:** قائمة مفلترة حسب الدور · فورم إضافة/تعديل · صفحة تفاصيل · أرشفة (فردية + تحديد الكل) · **استيراد Excel** · **فلتر "عملاء الموظفين المعطّلين"**

**معايير القبول:**
- موظف مبيعات ← يشوف عملاءه بس · الـ Team Leader يشوف فريقه · الـ Manager يشوف الكل
- استيراد Excel بحقول ناقصة ← السجل يتحفظ معلّم **"غير مكتمل"** ويظهر في فلتر مخصص
- اسم شبيه بعميل موجود ← **تحذير أصفر**؛ الموظف هو اللي يقرر
- عميل متأرشف يدويًا ← الـ Manager والـ Team Leader بس هما اللي يشوفوه
- تغيير مالك المبيعات ← العميل وكل تاريخه بينتقلوا + سطر audit

---

### Module 4 — الكتالوج والموردين
**User story:** كموظف مبيعات، عايز أتصفح كتالوج المنتجات/الخدمات وقائمة الموردين، علشان أبني عرض سعر.

**الجداول:** `catalog_items` · `suppliers`

**معايير القبول:**
- منتج جديد ← يظهر تحت تبويب المنتجات، مجمّع حسب الشركة
- مورد تقييمه أحمر ← الشريحة الحمرا تظهر جنب اسمه في **كل** الشاشات
- خدمة ← تظهر تحت تبويب الخدمات، منفصلة عن المنتجات
- منتج معطّل ← يتخفي من قوائم الاختيار الجديدة

---

### Module 5 — الطلبات / الصفقات ⭐
**User story:** كـ Team Leader، عايز أدخّل طلبات العملاء وأوزّعها على الموظفين، علشان الشغل يمشي في المسار الصح.

**الجداول:** `deals` · `deal_documents` · `deal_status_history`
**بالإضافة لمحرك حالة العميل** (`recompute_customer_status`)

**نقاط الـ API:**
```
CRUD  /api/v1/deals
PATCH /api/v1/deals/:id/assign · /approve · /reject · /status
POST  /api/v1/deals/:id/documents
```

**الواجهة:** شاشة الطلبات · فورم الإدخال · "عملائي" بعلامة الصفقة الحالية · **timeline الصفقة**

**معايير القبول:**
- عميل عنده صفقة نشطة ← لما يتضاف طلب جديد ← **صفقتين مستقلتين** بحالات منفصلة
- الصفقة توصل `Won` ← حالة العميل تبقى **"عميل"** تلقائيًا وبشكل دائم
- كل صفقات العميل `Lost` ← حالته تبقى **"صفقة لم تكتمل"**
- طلب مدخّل من موظف ← يظهر للـ Team Leader كـ "في انتظار الموافقة" ويفضل غير نشط لحد الموافقة
- طلب مرفوض ← سبب إجباري + شارة للموظف
- تغيير حالة ← سطر في الـ timeline بالحالة القديمة والجديدة ومين وإمتى

---

### Module 6 — عروض أسعار الموردين
**User story:** كموظف مبيعات، عايز أسجّل عرض سعر المورد وأرفق ملفه، علشان أستخدمه في بناء عرض العميل.

**الجداول:** `supplier_quotations` (بـ `deal_id` **قابل للفراغ**) · `supplier_quotation_items`

**معايير القبول:**
- عرض فيه منتج مش في الكتالوج ← المنتج بيتضاف تلقائيًا
- العرض اتحفظ ← يظهر تلقائيًا في صفحة المورد تحت "العروض المرتبطة"
- عرض مش مربوط بصفقة ← يتحفظ عادي ويبقى متاح لأي صفقة
- رفع ملف ← النوع والحجم والـ MIME الحقيقي بيتفحصوا + التخزين باسم UUID

---

### Module 7 — عروض أسعار العملاء ⭐ (أصعب موديول)
**User story:** كموظف مبيعات، عايز أبني عرض سعر لعميلي باستخدام أسعار الموردين وهامش ربح، علشان أبعته بعد موافقة الـ Team Leader.

**الجداول:** `quotations` · `quotation_items` · `quotation_additional_items` · `user_term_suggestions`

**نقاط الـ API:**
```
POST  /api/v1/quotations
GET   /api/v1/quotations/:id
PATCH /api/v1/quotations/:id/submit-for-approval
POST  /api/v1/quotations/:id/new-version
GET   /api/v1/quotations?group_by=employee|customer
```

**الواجهة:** باني عرض السعر — موردين ديناميكيين بـ (+) لحد 10 · منتجات لكل مورد · حساب لحظي · معاينة تأكيد قبل الحفظ · SmartTermInput للشروط

**معايير القبول (أهم حاجة في المشروع):**
- تكلفة 1000 وهامش 20% ← سعر البيع **1200** تلقائيًا
- هامش العرض 20% وهامش السطر 30% ← السطر بياخد **30%**
- موردين بعملات مختلفة ← التحويل بسعر الصرف الحالي وعملة واحدة للعرض
- إجمالي 1234.67 جنيه ← الإجمالي النهائي **1235** و `rounding_diff` = **0.33**
- إجمالي 1234.678 دولار ← الإجمالي النهائي **1234.68** (وحدة التقريب 0.01)
- كمية أعلى من المسجّل عند المورد ← **تحذير أحمر داخل السطر**
- منتج من غير سعر مسجّل ← **الحفظ ممنوع**
- سعر المورد اتغيّر بعد بناء العرض (`Draft`) ← تحذير + زرار "تحديث الأسعار"
- الموظف والـ Team Leader بيعدّلوا في نفس اللحظة ← **409 Conflict**

---

### Module 8 — الموافقات
**User story:** كـ Team Leader، عايز أراجع عروض الأسعار وأعدّل الضريبة والهامش قبل الموافقة، علشان أحمي هامش الشركة.

**نقاط الـ API:** `PATCH /:id/approve` · `/return` · `/edit-and-approve`

**معايير القبول:**
- تعديل ضريبة أو هامش ← **سطر audit إجباري** بالقيمة القديمة والجديدة
- عرض مرتجع ← ملاحظة إجبارية + العرض يرجع `Draft` ويظهر تحت "غير مكتمل"
- Team Leader بيوافق على عرضه هو ← `is_self_approved = true` + **شارة صفرا** + سطر audit نوعه `SELF_APPROVAL`
- عرض مستني أكتر من الـ SLA ← شارة حمرا + عمود "أيام الانتظار"
- الـ Team Leader والـ Manager ← **نفس الشاشة ونفس الصلاحية**

---

### Module 9 — توليد الـ PDF
**User story:** كموظف مبيعات، عايز أطلّع عرض سعر PDF محترم، علشان أبعته للعميل.

**معايير القبول:**
- عرض فيه 3 موردين ← **مفيش اسم مورد ولا سعر مورد في أي حتة في الـ PDF**
- توليد الـ PDF ← غير متزامن على طابور `pdf` + متخزن مع العرض + لقطة ثابتة
- فشل التوليد ← إعادة محاولة تلقائية + إشعار للموظف
- `show_delivery_terms = false` ← القسم ده يتشال
- الـ CEO ← يقدر **ينزّل** الـ PDF الموجود بس ما يقدرش يولّد جديد

---

### Module 10 — رد العميل وأوامر الشراء
**User story:** كموظف مبيعات، عايز أسجّل رد العميل، علشان الصفقة تمشي في المسار الصح.

**الجداول:** `purchase_orders` (رقم `po_number` تلقائي + `customer_po_reference` نص حر + تاريخ + مرفق)

**معايير القبول:**
- `Partial` أو `Counter` ← نسخة كاملة بتتحفظ تلقائيًا والموظف يعدّل في النسخة الجديدة
- `Counter` أو `Rejected` ← **سبب إجباري** قبل قبول الحالة
- `Rejected` ← العرض يتأرشف · **العميل يفضل في القائمة** · الصفقة تبقى `Lost`
- `valid_until` عدّى من غير رد ← **`Expired`** تلقائيًا (J-01)
- أمر شراء ← البحث شغال على الرقم الداخلي وعلى رقم العميل

---

### Module 11 — المشتريات
**User story:** كموظف مشتريات، عايز أعيد التفاوض مع المورد وأحسب الربح النهائي، علشان الشركة تكسب أحسن هامش ممكن.

**الجداول:** `procurement_negotiations`

**معايير القبول:**
- تفاوض ناجح من 1000 لـ 900 ← توفير 100 بيتسجّل ويتضاف للربح النهائي
- تفاوض فاشل ← محاولة فاشلة بسبب، والصفقة تكمّل بالسعر الأصلي
- المشتريات بتفتح عرض سعر ← بتشوف **التكلفة والهامش والربح**
- `Delivery Complete` ← أي واحد من الأربعة يقدر يأكّدها **مع تسجيل مين عملها**

---

### Module 12 — الزيارات الخارجية 📱
**User story:** كموظف خارجي، عايز أسجّل نتيجة الزيارة من موبايلي بأقل كتابة، علشان أخلّص يومي بسرعة.

**الجداول:** `visits` · `visit_areas`

**معايير القبول:**
- فورم الزيارة ← **3 حقول إجبارية بس**: اسم الشركة · الشخص المسؤول · النتيجة
- الكتابة والنت بيقطع ← المسودة بتتحفظ محليًا وما بتضيعش
- نتيجة "ناجحة" مع طلب ← الطلب بيتوجّه تلقائيًا للـ Team Leader وبيتعلّم "تم"
- رفض ← سبب إجباري، بيغذّي تقرير الشركات الرافضة
- الـ VPN مفصول ← **رسالة واضحة ومحددة**، مش خطأ عام
- المشرف ← يشوف الزيارات بس، و**ما يشوفش** أي صفقة بعد التسليم

---

### Module 13 — التقارير
**User story:** كموظف، عايز أرفع تقاريري علشان توصل للـ Team Leader، وعلشان الإدارة تتابع الشغل.

**الجداول:** `reports` · `report_recipients` · `report_versions`
**المهام:** J-04 · J-05 · J-06 · J-07 · J-08

**معايير القبول:**
- تقرير مرفوع ← **لقطة ثابتة + PDF متخزن**، ما بيتغيرش حتى لو البيانات الأصلية اتغيرت
- تقرير مرتجع ← سبب إجباري + نسخة v2، والأصلية محفوظة
- `Acknowledged` ← **للقراءة بس حتى لصاحبه**
- نفس النوع والفترة والموظف ← تحذير واختيار
- الـ CEO ← عرض وتصدير وتعليق بس — **مفيش اعتماد ومفيش إرجاع**
- السيرفر كان واقع يوم التقرير الأسبوعي ← المهمة **بتشتغل عند التشغيل** (catch-up)

---

### Module 14 — لوحة المعلومات
**User story:** كـ Manager، عايز أشوف المبيعات والأرباح لفترة، علشان أتابع الأداء.

**الجداول:** جداول تجميعية (pre-aggregation) — مهمة J-09

**معايير القبول:**
- فترة محددة ← الأرقام تطابق البيانات الأصلية بالظبط
- عملتين ← كل واحدة تتعرض لوحدها، والتجميع اختياري
- الـ CEO ← **مفيش drill-down** على أي رقم
- "المبيعات حسب المنطقة" ← تفضل ورا feature flag
- ❌ **مش في الـ MVP:** المدفوعات المستحقة · الشيكات المستحقة

---

### Module 15 — البحث (Meilisearch)
**User story:** كمستخدم، عايز أبحث بالعربي بسرعة وألاقي نتايج حتى لو كتبت غلط.

**التنفيذ:** استبدال `PostgresSearchDriver` بـ `MeilisearchDriver` جوه `SearchService`

**معايير القبول:**
- البحث عن "احمد" ← "أحمد" بتتلاقي (تطبيع الهمزة)
- خطأ إملائي بسيط ← النتايج تفضل تظهر (تسامح الأخطاء)
- موظف مبيعات ← يبحث في عملاءه بس (فلترة الصلاحيات)
- Meilisearch واقع ← النظام يرجع لـ ILIKE تلقائيًا؛ **الشاشة ما بتتكسرش**
- إنشاء أو تعديل ← الفهرسة بتحصل فورًا عبر مهمة

## 3. ⚠️ شرط إجباري على تأجيل البحث (D-48)

تأجيل Meilisearch للآخر مقبول **بشرط واحد**: إن كل نداء بحث في الكود يعدّي على `SearchService` من Module 3.

```
SearchService.search(index, query, filters)
   ├── أول تنفيذ: PostgresSearchDriver (ILIKE)
   └── التنفيذ النهائي: MeilisearchDriver
```

من غير الطبقة دي، إضافة Meilisearch في الآخر معناها **إعادة كتابة كل شاشة فيها شريط بحث**.

📏 **مؤشر القياس:** لو بحث العملاء عدّى **500 مللي ثانية** في أي وقت، قدّم Module 15 فورًا بدل ما تستنى.

> الرفع ابتدا من Module 1، فده تجهيز للإنتاج، **مش أول رفع**.

- PostgreSQL + Redis + Meilisearch على السيرفر
- Nginx كـ reverse proxy + SSL
- مدير عمليات بـ **تشغيل تلقائي عند الإقلاع** لكل خدمة، بالترتيب الصح
- **نسخ احتياطي يومي: داتابيز + ملفات + Meilisearch — على جهاز/قرص منفصل**
- **اختبار استرجاع حقيقي** — مش مجرد التأكد إن الملف موجود
- **مراقبة خارجية (heartbeat)**
- كتيبات تشغيل: الاسترجاع · بدء التشغيل · الرفع · التراجع

### 4.3 الإطلاق التجريبي
- **استيراد البيانات القديمة من Excel** + جلسة لاستكمال السجلات الناقصة يدويًا

استراتيجية الاختبار · خطة الاختبار

### 5.1 المعيار الأساسي

### 5.2 معايير مساندة
