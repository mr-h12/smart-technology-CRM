# نظام CRM — عقد الـ OpenAPI

> ⚠️ **للقراءة بس.** الملف ده مش جزء من النظام وعمره ما هيتستخدم في التنفيذ. المرجع الرسمي هو النسخة الإنجليزية، والملف ده ممكن يكون قديم.

> **الحالة:** أساس مطلوب قبل أول endpoint.
> **الإصدار:** `v1`
> **التوأم:** `OpenAPI_Contract_EN.md` — لازم الاتنين يفضلوا متطابقين دلاليًا.

## 1. الغرض والمرجعية

العقد ده بيعرّف الاتفاقيات العامة للـ API المطلوبة في `API-01` لحد `API-12`: تسمية موارد REST، وترقيم الإصدار `/api/v1/`، وأظرف النجاح/الخطأ الموحّدة، والـ pagination، والفلترة، والتجميع، وتحديد المعدل، وسجلات الـ API، وتوثيق OpenAPI، والتزامن التفاؤلي.

بينطبق على الـ SPA والـ PWA الداخليين. **وما بيخفّفش** مصفوفة الصلاحيات ولا قواعد الشغل ولا متطلبات الـ audit ولا نموذج البيانات ولا النطاق. ولو مواصفة موديول احتاجت قاعدة مش معرّفة هنا، **مستندات الـ CRM الأساسية هي الحكم**.

## 2. الاتفاقيات الأساسية

| البند | العقد |
|---|---|
| المسار الأساسي | `/api/v1` |
| الأسلوب | JSON عبر HTTPS بأسلوب REST. أسماء موارد بصيغة الجمع و kebab-case: `/supplier-quotations`، **مش أفعال في المسارات**. |
| ترميز الحروف | UTF-8 JSON. |
| تسمية الحقول | `snake_case` في الطلب والرد. |
| معرّفات الموارد | UUID غير شفاف. وأكواد الشغل المقروءة (`DL-…`, `QT-…`, `SQ-…`, `PO-…`, `RPT-…`) **بتفضل حقول منفصلة**. |
| التواريخ والأوقات | ISO 8601 بـ UTC (`2026-08-11T13:45:30Z`). والعميل بيعرضها بتوقيت المستخدم. |
| التواريخ فقط | ISO 8601 (`YYYY-MM-DD`). |
| الفلوس | القيم العشرية **نصوص JSON، عمرها ما تكون أرقام عائمة**. وكل تركيب مالي بيحمل المبلغ والعملة وسعر الصرف الملتقط والمبلغ الأساسي حيث ينطبق. |
| نوع المحتوى | الطلبات `Content-Type: application/json` إلا عند رفع الملفات. والردود `application/json` إلا عند بث تنزيل مسموح. |
| اللغة | العميل بيبعت `Accept-Language: ar` أو `en`. **والأكواد الآلية بتفضل إنجليزي**؛ والرسائل الظاهرة للمستخدم مترجمة. |

### 2.1 ترقيم إصدار الـ API

- كل الـ endpoints بتبدأ بـ `/api/v1` من أول يوم.
- أي تغيير كاسر في العقد العام محتاج إصدار جديد (`/api/v2`)؛ **ومتعيدش استخدام حقل أو كود حالة في الصمت**.
- الحقول الاختيارية الإضافية مسموحة في `v1` لما تكون موثّقة في OpenAPI.
- كل إصدار منشور بيطلّع مستند OpenAPI وسجل تغييرات مرقّم.

## 3. المصادقة والصلاحيات والتتبع

### 3.1 المصادقة

- نقاط المستخدم بتتطلب جلسة مستخدم نشطة ومصادَقة أو بيانات اعتماد مكافئة صادرة من السيرفر.
- **المتصفح عمره ما يستقبل بيانات اعتماد داتابيز أو خدمات ذات امتيازات.**
- مفاتيح الـ API والـ webhooks محجوزة لقدرة تكامل الـ API الموثّقة، ولازم تكون محدودة النطاق ومحدودة المعدل وقابلة للتدقيق والإلغاء، **وعمرها ما تكون بديل لجلسة موظف**.
- الحسابات المعطّلة أو المقفولة أو المنتهية أو اللي اتعمل لها خروج إجباري **مش بتقدر تنادي نقاط محمية**.

### 3.2 الصلاحيات

- **كل endpoint بيفرض صلاحيات `resource.action.scope` ديناميكية من الداتابيز على مستوى الـ API والصف.**
- السيرفر هو اللي بيحدد كل النطاقات: `Own` و `Team` و `All` و `Out` و `Asgn`. ومعاملات الاستعلام **ممكن تضيّق** نتيجة مسموحة، **وعمرها ما توسّعها**.
- **ظهور الواجهة مش صلاحية.** وأي طلب API مباشر من غير صلاحية **لازم يفشل**.
- **صلاحية التصدير/التنزيل عمرها ما تتعدى صلاحية العرض.**
- نقاط PDF العميل **بتستبعد دايمًا** أسماء الموردين وأسعارهم والتكاليف والهوامش، **مهما كان دور اللي بينادي**.

### 3.3 معرّفات الطلب والـ Audit

| الـ Header | الاتجاه | القاعدة |
|---|---|---|
| `X-Request-Id` | الرد | معرّف فريد بيولّده السيرفر ويرجع في كل رد. ضمّنه في السجلات والأخطاء وربط الـ audit وتقارير الدعم. |
| `X-Correlation-Id` | طلب/رد | معرّف تتبع اختياري من المنادي. افحصه ومرّره؛ وإلا اعمل واحد. **وعمرك ما تثق فيه كمدخل صلاحية.** |
| `Idempotency-Key` | الطلب | مطلوب لنقاط الإنشاء/الإجراء الحرجة المحددة؛ UUID أو مفتاح عالي العشوائية من العميل. |
| `If-Match` | الطلب | مطلوب لتعديلات عروض الأسعار الخاضعة للقفل التفاؤلي؛ وبيحمل رمز نسخة العرض الأحدث. |

**كل التعديلات المصادَق عليها لازم تعمل سطر الـ audit المطلوب على السيرفر. والعملاء مش بيقدروا يكتبوا صفوف audit مباشرة.**

## 4. ظرف الرد الموحّد

### 4.1 نجاح مورد واحد

بيتستخدم لـ `GET` التفاصيل و `POST` الإنشاء وردود `PATCH`/الإجراءات الناجحة.

```json
{
  "data": {
    "id": "018f6a2c-2e7e-7d9a-a5e8-3b329495aa10",
    "code": "QT-2026-0001"
  },
  "meta": {
    "request_id": "req_01J5Y8P7TJ1J8DNM7ED6K2D1XQ"
  }
}
```

### 4.2 نجاح مجموعة

**كل نقطة قائمة بـ pagination؛ والـ endpoint عمره ما يرجّع مجموعة غير محدودة.**

```json
{
  "data": [],
  "meta": {
    "pagination": {
      "page": 1,
      "per_page": 25,
      "total": 142,
      "total_pages": 6,
      "has_next_page": true,
      "has_previous_page": false
    },
    "request_id": "req_01J5Y8P7TJ1J8DNM7ED6K2D1XQ"
  }
}
```

### 4.3 شغل غير متزامن مقبول

استخدم `202 Accepted` للشغل اللي بيتحط في طابور، بما فيه توليد الـ PDF وتوليد التقارير حيث ينطبق.

```json
{
  "data": {
    "job_id": "018f6a34-1ef9-7bda-bfe8-56e4e152cc44",
    "status": "queued"
  },
  "meta": {
    "request_id": "req_01J5Y8P7TJ1J8DNM7ED6K2D1XQ"
  }
}
```

عقد الموديول بيحدد مين يقدر يشوف حالة المهمة وإيه المخرج المتاح بعد الاكتمال. **ورد `202` مش دليل إن الـ PDF أو التقرير جاهز.**

## 5. ظرف الخطأ الموحّد

كل الردود غير 2xx بتستخدم الشكل ده. **عمرك ما ترجّع HTML افتراضي من إطار العمل أو كائن خطأ غير مهيكل.**

```json
{
  "error": {
    "code": "validation_failed",
    "message": "من فضلك صحّح الحقول المميّزة.",
    "details": [
      {
        "field": "valid_until",
        "code": "required",
        "message": "تاريخ الصلاحية مطلوب."
      }
    ]
  },
  "meta": {
    "request_id": "req_01J5Y8P7TJ1J8DNM7ED6K2D1XQ"
  }
}
```

### 5.1 أكواد الأخطاء وحالات HTTP

| HTTP | `error.code` | الاستخدام |
|---:|---|---|
| 400 | `invalid_request` | JSON مشوّه، أو صيغة استعلام غلط، أو header غلط. |
| 401 | `authentication_required` / `session_invalid` | مصادقة ناقصة أو منتهية أو مقفولة أو غلط. |
| 403 | `permission_denied` | المنادي مصادَق عليه بس مش مسموح له بالإجراء. |
| 404 | `resource_not_found` | المورد مش موجود أو مش ظاهر للمنادي. **متكشفش أنهي حالة منهم.** |
| 409 | `concurrency_conflict` | نسخة عرض السعر قديمة. رجّع بيانات النسخة الحالية اللازمة للتحديث، **وعمرك ما تكتب فوقها في الصمت**. |
| 409 | `idempotency_conflict` | نفس مفتاح الـ idempotency استُخدم بحمولة أو عملية مختلفة. |
| 409 | `state_transition_invalid` | تغيير الحالة المطلوب بيخالف المسار الموثّق. |
| 422 | `validation_failed` | طلب سليم الشكل بس فشل في تحقق الشغل أو الحقول. |
| 422 | `business_rule_blocked` | قاعدة موثّقة بتمنع الإجراء، زي غياب سعر المورد. |
| 423 | `account_locked` | الحساب مقفول بعد محاولات دخول فاشلة. |
| 429 | `rate_limit_exceeded` | تجاوز الحد. رجّع `Retry-After`. |
| 500 | `internal_error` | فشل غير متوقع. سجّله داخليًا؛ **وعمرك ما تكشف** stack trace ولا SQL ولا أسرار ولا بيانات حساسة. |
| 503 | `service_unavailable` | فشل مؤقت في تبعية أو صيانة. رجّع رسالة إعادة محاولة آمنة. |

استخدم أكواد ثابتة ومحددة جوه `details` للقواعد المتوقعة، مثلاً `supplier_price_missing` و `rejection_reason_required` و `quantity_exceeds_recorded` و `file_mime_invalid`.

## 6. عقد الاستعلام للقوائم

### 6.1 الـ Pagination

```text
GET /api/v1/customers?page=1&per_page=25
```

- `per_page` الافتراضي: `25`؛ والأقصى `100`. والقيم غير الصالحة أو الزايدة بترجّع `400 invalid_request`.
- `total` مطلوب لما الاستعلام يقدر يحسبه بكفاءة. ولو نقطة متخصصة مش قادرة، **مواصفة OpenAPI بتاعة الموديول لازم تحدد البديل قبل التنفيذ**.
- **الـ pagination بيحصل دايمًا بعد تحديد نطاق الصلاحيات وقبل تسلسل الرد.**

### 6.2 الفلترة والبحث والترتيب والتجميع

```text
GET /api/v1/quotations?filter[status]=pending&filter[currency]=EGP
GET /api/v1/customers?q=ahmed&sort=-created_at,name
GET /api/v1/quotations?group_by=<مجموعة-موثّقة>
```

| المعامل | القاعدة |
|---|---|
| `filter[field]` | بيدعم الحقول المعلنة صراحةً للمورد ده بس. كرّر المعامل للفلتر متعدد القيم المسموح. |
| `q` | استعلام بحث محدود بالصلاحيات. **بيعدّي دايمًا على `SearchService`**؛ ومتكشفش صيغة بحث خاصة بالداتابيز. |
| `sort` | حقول مسموحة مفصولة بفاصلة. والبادئة `-` تعني تنازلي؛ والترتيب الافتراضي خاص بالمورد وموثّق. |
| `group_by` | التجميع على السيرفر بس. وكل مورد بيعلن مجموعاته المسموحة؛ **والعملاء مش بيطلبوا تجميع داتابيز عشوائي**. |
| `include` | توسيع اختياري للبيانات المرتبطة، محدود بالعلاقات الموثّقة والآمنة للصلاحيات. **عمرك ما تستخدمه لتخطي نقطة التفاصيل أو إرجاع مجموعات غير مقيّدة.** |

**ارفض قيم الفلتر أو الترتيب أو التجميع أو التضمين غير المعروفة بـ `400 invalid_request`؛ وعمرك ما تتجاهلها في الصمت.**

## 7. اتفاقيات الموارد والإجراءات

### 7.1 مسارات الموارد

استخدم المسارات التقليدية:

```text
GET    /api/v1/customers
POST   /api/v1/customers
GET    /api/v1/customers/{customer_id}
PATCH  /api/v1/customers/{customer_id}

GET    /api/v1/deals
POST   /api/v1/deals
GET    /api/v1/deals/{deal_id}
PATCH  /api/v1/deals/{deal_id}

GET    /api/v1/quotations
POST   /api/v1/quotations
GET    /api/v1/quotations/{quotation_id}
PATCH  /api/v1/quotations/{quotation_id}
```

استخدم نفس التركيب للموردين وأصناف الكتالوج وعروض الموردين وأوامر الشراء والمفاوضات والزيارات والتقارير والمستخدمين والأدوار والصلاحيات والعملات وأسعار الصرف والإعدادات وموارد الإدارة المسموحة.

### 7.2 إجراءات المجال

استخدم لاحقة إجراء واضحة **بس لما الإجراء ميكونش تعديل مورد عادي** وبيمثّل أمر مجال موثّق.

```text
PATCH /api/v1/customers/{customer_id}/assign
PATCH /api/v1/customers/{customer_id}/archive
PATCH /api/v1/customers/{customer_id}/restore

PATCH /api/v1/deals/{deal_id}/approve
PATCH /api/v1/deals/{deal_id}/reject
PATCH /api/v1/deals/{deal_id}/status

PATCH /api/v1/quotations/{quotation_id}/submit-for-approval
PATCH /api/v1/quotations/{quotation_id}/approve
PATCH /api/v1/quotations/{quotation_id}/return
POST  /api/v1/quotations/{quotation_id}/new-version
```

- كل إجراء له سكيما طلب صريحة وصلاحية مطلوبة وحدث audit وحالة حالية مقبولة وحالة ناتجة ومتطلب idempotency في مستند OpenAPI المولّد.
- **عمرك ما تستخدم نقاط عامة** زي `/update-status` أو `/action` أو `/bulk` من غير مورد ومعنى مجال موثّق.
- استخدم `POST` لإنشاء نسخة جديدة أو مورد فرعي غير idempotent؛ واستخدم `PATCH` لتعديل حالة/إجراء مصرّح به على مورد موجود.

### 7.3 العمليات الجماعية

الأرشفة/الاسترجاع الجماعي مسموحة **بس حيث مستندات الـ CRM بتسمح**. استخدم إجراء خاص بالمورد وقائمة معرّفات محدودة:

```json
{
  "ids": ["uuid-1", "uuid-2"]
}
```

رجّع نتيجة لكل سجل. **وافحص الصلاحية وسجّل الـ audit لكل سجل متأثر؛ ومتسمحش للطلب الجماعي إنه يتخطى نطاق الصف.**

## 8. قواعد تمثيل البيانات

### 8.1 الفلوس

```json
{
  "amount": "1234.67",
  "currency": "EGP",
  "fx_rate_at_time": "1.000000",
  "base_amount": "1234.67"
}
```

- **الـ backend بيحسب ويفحص ويقرّب ويحفظ كل القيم المالية.**
- نصوص المبالغ بتستخدم `.` كفاصل عشري **ومن غير فاصل آلاف**.
- الطلب ممكن يبعت مبالغ مدخلة مسموحة؛ **وإجماليات الرد هي نتايج الـ backend المعتمدة**.
- **حافظ على اللقطات المالية في نسخ عروض الأسعار/التقارير.** وتعديل العملة أو إعدادات الصرف الحالية **عمره ما يغيّر رد تاريخي**.

### 8.2 العلاقات وحقول الـ Audit

- مثّل العلاقات المباشرة بحقول معرّفات صريحة زي `customer_id` و `deal_id` و `owner_id`.
- ضمّن كائنات عرض خفيفة **بس لما عقد `include` بتاع المورد يسمح**.
- ردود القراءة بتضمّن بيانات الـ audit المنطبقة (`created_by`, `created_at`, `updated_by`, `updated_at`) **حسب الصلاحية**. وسجل الـ audit الكامل غير القابل للتغيير **مورد منفصل**.
- **حالة الحذف الناعم/الأرشفة/التعطيل لازم تكون صريحة** لما يكون المنادي مسموح له يشوفها؛ **وعمرك ما تموّه الأرشفة كحذف فعلي**.

### 8.3 الملفات والتنزيلات

- نقاط الرفع المتعدد لازم تعلن أنواع الـ MIME المسموحة والحجم الأقصى القابل للضبط وحالة فحص الفيروسات والكيان الأب.
- **الملف المخزن عمره ما يكون قابل للعنونة العامة.** والتنزيل بيستخدم نقطة بتفحص الصلاحية **وبتعيد الفحص وقت الطلب**.
- توليد الـ PDF غير متزامن. ونقطة PDF عرض سعر العميل بتتبع قاعدة التوليد/التنزيل الخاصة بالدور **وعمرها ما تكشف حقول موردين أو مالية داخلية**.

## 9. الـ Idempotency والتزامن

### 9.1 الـ Idempotency

اطلب `Idempotency-Key` لأوامر `POST` الحرجة، بما فيها إنشاء الصفقات وعروض الأسعار وعروض الموردين وأوامر الشراء والتقارير والنسخ والإجراءات اللي بتغيّر حالة شغل مكافئة لغير القابل للتراجع.

- احفظ الفاعل والمسار والمفتاح وبصمة الطلب والحالة النهائية والرد لمدة الاحتفاظ المحددة.
- **تكرار نفس الفاعل + المسار + المفتاح + الحمولة بيرجّع الرد الأصلي من غير تكرار الأثر الجانبي.**
- إعادة استخدام مفتاح بحمولة متغيّرة أو إجراء مختلف بترجّع `409 idempotency_conflict`.
- **الـ idempotency مش بديل للصلاحيات:** كل إعادة محاولة بتتفحص على جلسة نشطة وصلاحية حالية.

### 9.2 التزامن التفاؤلي

- قراءات عرض السعر بترجّع رمز النسخة الحالية، مثلاً `"etag": "quotation:uuid:7"`.
- تعديل عرض السعر بيبعت الرمز ده في `If-Match`.
- **لو النسخة المخزنة مختلفة، رجّع `409 concurrency_conflict`** بمرجع تحديث آمن. **متدمجش ومتكتبش فوق تلقائيًا.**
- نفس النمط ممكن يتبنى بعدين لموارد تانية عالية التنافس **بتحديث موثّق للعقد بس**.

## 10. حدود المعدل والسجلات والتوثيق

- حُدّ معدل الدخول ونقاط الـ API حسب المستخدم وبيانات الاعتماد والـ IP والنقطة حسب المناسب. **والحدود الفعلية إعدادات نظام قابلة للضبط، مش ثوابت في العميل.**
- سجّل الفاعل/بيانات الاعتماد والوقت ومعرّف الطلب ومعرّف الارتباط والنقطة والطريقة وحالة الرد والـ IP وبيانات الجهاز/العميل والمدة وكود الخطأ الآمن. **وعمرك ما تسجّل كلمات سر أو رموز أو أسرار أو حمولات حساسة خام من غير داعي.**
- انشر OpenAPI 3.1 JSON المولّد وتوثيق مقروء لكل إصدار. **والعقد جزء من الـ CI:** مسارات التنفيذ وسكيمات الطلب والرد ومعرّفات العمليات الموثّقة لازم يفضلوا متزامنين.
- **اختبر كل عملية محمية باختبارات صلاحيات سلبية على مستوى الـ API؛ واختبارات الواجهة وحدها مش كافية.**

## 11. معايير قبول عقد الـ API

1. لطلب تفاصيل أو إنشاء ناجح، لما السيرفر يرد، بيستخدم ظرف المورد الواحد وبيضمّن `meta.request_id`.
2. لأي نقطة قائمة، لما المنادي يسيب الـ pagination، السيرفر بيرجّع الصفحة الافتراضية المحدودة وبيانات الـ pagination.
3. لحقل غير صالح أو قاعدة شغل، لما السيرفر يرفضه، بيرجّع رسالة مترجمة وكود آلي ثابت وتفاصيل الحقول حيث ينطبق **ومن غير stack trace داخلي**.
4. لمستخدم من غير صلاحية، لما ينادي نقطة مباشرة، السيرفر **بيرفض الوصول مهما كانت حالة الواجهة وما بيكشفش وجود سجل غير متاح**.
5. لعرض سعر اتعدّل من مستخدم تاني، لما يتبعت رمز `If-Match` قديم، السيرفر بيرجّع `409 concurrency_conflict` **وبيحافظ على العرض الحالي وتاريخ الـ audit**.
6. لأمر حرج متكرر بنفس مفتاح الـ idempotency والحمولة، لما يتعاد، بيرجّع النتيجة الأصلية **من غير سجل شغل أو حدث audit مكرر**.
7. لرد API فيه قيمة مالية، القيمة دي متسلسلة **كنص عشري بسياق العملة/الصرف المطلوب**.
8. لطلب PDF موجّه للعميل، لما يكون المنادي مصرّح له، المحتوى المولّد/المنزّل **بيفضل مستبعد منه أسماء الموردين وأسعارهم والتكلفة والهامش**.
