# نظام CRM — معايير الكود

> **الحالة:** معيار هندسي إجباري قبل التنفيذ.
> **النطاق:** محايد تجاه إطار العمل؛ بينطبق على كل كود الـ backend والـ frontend والداتابيز والعمّال والبنية التحتية.
> **المرجعية:** `CRM_Documentation_EN.md` يفضل مصدر الحقيقة للمنتج. ولو الملف ده اتعارض معاه، **مستندات الـ CRM هي الصح**.
> **التوأم:** `Coding_Standards_EN.md` — لازم الاتنين يفضلوا متطابقين دلاليًا.

## 1. الغرض وترتيب الأسبقية

المعايير دي بتخلّي التنفيذ آمن وقابل للمراجعة والاختبار ومتّسق، لنظام بيتعامل مع فلوس وصلاحيات وتاريخ غير قابل للتغيير وبيانات تشغيلية.

استخدم ترتيب الأسبقية ده:

1. سجل قرارات الـ CRM المعتمد والمتطلبات الأساسية.
2. خطة بناء الـ MVP ومعايير قبول موديولاتها.
3. معيار الكود ده.
4. عقد الـ OpenAPI، ونظام التصميم، والشخصيات، ومواصفات الموديولات.
5. الأداة أو الـ plugin أو إطار العمل أو التفضيل الشخصي.

**لو المتطلب غامض أو ناقص أو متناقض، قف واطلب قرار موثّق. متحلّهوش في الكود في الصمت.**

## 2. انضباط الشغل

- حوّل كل مهمة لمعايير نجاح قابلة للملاحظة قبل ما تغيّر كود.
- لأي تغيير بيمس أكتر من ملف، اعرض `خطوة → تحقق` **وخُد الموافقة قبل التعديل**.
- اعمل أصغر تغيير متماسك. **متخلطش** إعادة هيكلة أو تنسيق أو ترقية تبعيات أو تنظيف كود ميت مع شغل الميزات.
- اقرا الأقسام المرتبطة بالمهمة بس، **بس ارجع اقراها** قبل ما تغيّر فلوس أو صلاحيات أو حالات مسار أو عروض أسعار أو تقارير أو ملفات.
- اذكر افتراضاتك صراحةً. **والافتراض غير المعتمد لازم يبان في ملاحظات المهمة وعمره ما يبقى قاعدة شغل مخفية.**
- **متعلّمش الشغل إنه خلص** قبل ما الفحوص المطلوبة تشتغل وتتقال نتايجها الحقيقية.

## 3. المعمارية وحدود الموديولات

### 3.1 الطبقات

حافظ على اتجاه التبعيات المطلوب:

```text
Presentation → Application → Domain → Infrastructure
```

| الطبقة | مسؤولياتها | ممنوع تحتوي على |
|---|---|---|
| Presentation | معالجات HTTP، وتحليل الطلب، وتسلسل الرد، ومكوّنات الواجهة، وتفاعل المستخدم. | حسابات شغل، أو قرارات صلاحيات، أو استعلامات داتابيز مباشرة. |
| Application | حالات الاستخدام، وتنسيق الـ transactions، واستدعاء الصلاحيات، وتنظيم الواجهات/الأحداث. | اهتمامات واجهة خاصة بإطار عمل، أو SQL خام متناثر في حالات الاستخدام. |
| Domain | كيانات الشغل، وكائنات القيمة، والسياسات، وانتقالات الحالة، وقواعد الحساب، وأحداث المجال. | HTTP، أو واجهة، أو إطار عمل، أو تخزين، أو طوابير، أو نداءات SDK خارجية. |
| Infrastructure | مستودعات الداتابيز، و adapter التخزين، و adapter الطوابير، و adapter الـ PDF، و adapters الخدمات الخارجية. | سياسات شغل غير محدودة أو منطق صلاحيات. |

### 3.2 الموديولات

خلّي الكود جوه الموديولات الموثّقة: الهوية، العملاء، الصفقات، عروض الأسعار، الموردين، الكتالوج، المشتريات، الميدان، التقارير، الإشعارات، الـ audit، والإدارة.

- الموديول بيملك قواعد مجاله وحالات استخدامه وواجهة التخزين وسطح الـ API بتاعه.
- **الموديول ممنوع يستورد جداول/مستودعات موديول تاني الخاصة علشان يغيّر بياناتها.**
- الشغل بين الموديولات بيستخدم واجهات معلنة أو أحداث مجال، وليه مالك واضح لسلوك الـ transaction/الـ audit الناتج.
- **متعملش منطقة "utils" مشتركة لمنطق الشغل.** حط القاعدة في الموديول اللي بيملكها أو في مكتبة تقنية مشتركة باسم واضح.

## 4. التسمية ووضوح الكود

- استخدم أسماء بتوصف مفهوم الشغل: `quotation` و `supplier_quotation` و `deal` و `customer`؛ **ومتدخّلش** مصطلحات بديلة زي `order` لصفقة CRM.
- استخدم قيم الحالات وأكواد المستندات الموثّقة بالظبط. **متعملش** مرادفات ولا enums في الكود بتبعد عن القوائم المُدارة في الداتابيز.
- سمّي الحقول المنطقية كسؤال أو حالة: `is_archived` و `is_active` و `is_self_approved` و `has_open_account`.
- سمّي حقول الوقت بدقة: `created_at` و `updated_at` و `valid_until` و `last_activity_at`؛ **وخزّن الأوقات بـ UTC**.
- سمّي حقول الفلوس بالمعنى والوحدة: `unit_cost` و `unit_cost_base` و `unit_price` و `line_total` و `gross_profit` و `final_profit`.
- خلّي الدوال مركّزة على حالة استخدام أو سياسة واحدة. وفضّل الأسماء الصريحة على التعليقات اللي بتشرح أسماء غامضة.
- التعليقات بتشرح القيود غير الواضحة أو القرارات أو حدود الأمن أو المراجع لـ `D-xx` و `DB-xx` و `J-xx` ومعايير القبول؛ **مش بتحكي syntax واضح**.

## 5. الأنواع والتحقق وسلامة البيانات

- استخدم typing صارم. **متدخّلش** مخارج غير مُنمّطة، ولا تحويل ضمني، ولا قيم nullable مخفية.
- **افحص كل قيمة غير موثوقة عند حدود الـ backend:** جسم الطلب، والاستعلام، والـ header، ومعامل المسار، وبيانات الملف، وحمولة الطابور، وإعدادات البيئة، ورد الـ adapter الخارجي.
- افحص الشكل وقواعد الشغل منفصلين لما يكون ده مفيد: فحص الشكل بيطلّع أخطاء حقول؛ وفحص المجال بيطلّع كود قاعدة شغل ثابت.
- **افرض الثوابت في الداتابيز زي ما بتفرضها في الكود:** foreign keys و check constraints و unique constraints والحقول المطلوبة والفهارس.
- اعتبر قيود الداتابيز هي **الحكم النهائي** تحت الطلبات المتزامنة. وحوّل أخطاء القيود المعروفة لأخطاء عقد آمنة؛ **وعمرك ما تكشف رسائل الداتابيز الخام**.
- استخدم جداول enum/مرجعية للقيم القابلة للتوسع. **عمرك ما تكتب** القطاعات ولا الوحدات ولا أنواع الخدمات ولا شروط التسليم ولا العملات ولا الصلاحيات في الكود.

## 6. الفلوس والعملات والحسابات

- **الـ Float ممنوع للفلوس.** استخدم `Decimal`/NUMERIC في التخزين وأنواع عشرية دقيقة في الكود.
- سلسل الفلوس كنصوص عشرية عند حدود الـ API، حسب `OpenAPI_Contract_EN.md`.
- **نفّذ كل الحسابات في طبقة الـ backend/الـ domain.** الواجهة ممكن تعرض نتيجة أكّدها السيرفر، **بس عمرها ما تبقى مصدر الحقيقة**.
- طبّق ترتيب الحساب الموثّق بالظبط. **متقرّبش القيم الوسيطة**؛ قرّب الإجمالي النهائي بس بالوحدة المضبوطة لعملته.
- خزّن المبلغ والعملة و `fx_rate_at_time` والمبلغ الأساسي حيث هو مطلوب. **وعمرك ما تعيد حساب عرض تاريخي** بسعر صرف أو سعر مورد أحدث.
- خلّي تكلفة المورد والهامش والتوفير والربح وسعر البيع للعميل **منفصلين دلاليًا** في الكود والـ schema والردود ونماذج الواجهة.
- **اكتب اختبارات وحدة مركّزة** لكل معادلة تسعير وحد تقريب وتحويل عملة وخصم وضريبة وبند إضافي وقاعدة توفير **قبل** ما تغيّر كود الحساب.

## 7. معايير الداتابيز والـ Migration

- كل تغيير في الـ schema بيتعمل بـ migration جديد ومُدار ومرقّم بمسارات `up` و `down` مختبرة.
- **عمرك ما تعدّل schema الإنتاج بإيدك. وعمرك ما تعدّل migration اتنفذ في أي بيئة مشتركة؛** ضيف migration مصحّح.
- كل جدول شغل فيه primary key و foreign keys وأعمدة audit وسلوك soft delete حسب `DB-01` و `DB-02`.
- ضيف فهارس لكل join ونطاق صلاحية وفلتر وترتيب وبحث شائع جديد. **وتأكد منها بخطط استعلام واقعية** للمسارات عالية الحجم.
- استخدم transactions لأي عملية بتمس أكتر من جدول، بما فيها تعديل السجل + سطر الـ audit، وإنشاء نسخة، وانتقال حالة، وإعادة إسناد، وربط بيانات ملف.
- **متستخدمش `DELETE` فعلي** لكيانات الشغل ولا التقارير ولا سجلات الـ audit ولا الملفات. استخدم الأرشفة/التعطيل/الحذف الناعم الموثّق.
- استخدم optimistic locking لعروض الأسعار. والكتابة القديمة بترجّع `409 concurrency_conflict`؛ **وعمرها ما تكتب فوق البيانات الحالية في الصمت**.
- البيانات الأولية مرقّمة وقابلة للتكرار: الأدوار والصلاحيات والقوائم المُدارة والعملات ومستخدمي الاختبار لازم يكونوا قابلين لإعادة الإنتاج في البيئات غير الإنتاجية.

## 8. معايير الـ API

- اتبع `OpenAPI_Contract_EN.md` لـ `/api/v1` وأظرف الـ JSON والأخطاء والـ pagination ومعاملات الفلترة/البحث/الترتيب/التجميع والـ idempotency وبيانات الرد.
- خلّي معالجات المسارات رفيعة: افحص وتحقق، نادِ حالة استخدام، بعدين سلسل النتيجة المعتمدة.
- **اعمل pagination لكل مجموعة. وعمرك ما تعمل endpoint بيرجّع "الكل"** لبيانات الشغل.
- طبّق الصلاحيات **قبل** جلب البيانات أو تعديلها؛ وفلاتر الاستعلام ممكن تضيّق النطاق **بس عمرها ما توسّعه**.
- استخدم أكواد أخطاء ثابتة وقابلة للقراءة آليًا. وترجم الرسائل حسب لغة الطلب؛ **ومتخليش العميل يحلّل نص الخطأ**.
- اطلب مفاتيح idempotency للعمليات الحرجة المحددة، **واحتفظ بالرد الأصلي** لإعادة المحاولة الصحيحة.
- خلّي سكيما OpenAPI وفواحص الطلبات ومسلسلات الردود والاختبارات متوافقين. **والمسار غير الموثّق هو مسار ناقص.**

## 9. الصلاحيات والأمن والخصوصية

- **افرض RBAC ديناميكي على مستوى الـ API والصف. إخفاء الزرار مش تحكم في الوصول أبدًا.**
- افحص صلاحية كل إجراء على السجل المستهدف وحالته الحالية، بما فيها الموارد المتداخلة والتنزيلات والعمليات الجماعية والتصدير وطلبات المهام غير المتزامنة.
- **اختبر حالة سلبية لكل عملية حساسة للصلاحيات:** اللي مش مصرّح له لازم يكون **مش قادر** يقرا ولا يستنتج ولا يعدّل ولا يصدّر ولا ينزّل البيانات.
- خلّي الأسرار برّه الكود والسجلات. **وعمرك ما تكشف** بيانات اعتماد خدمات أو رموز جلسات أو أكواد إعادة تعيين أو stack traces أو SQL أو مسارات داخلية في ردود المتصفح.
- طبّق تحديد المعدل على الدخول ونقاط الـ API؛ وافحص المدخلات؛ واحمِ من الحقن و XSS و CSRF؛ واستخدم HTTPS **حتى على الشبكة الداخلية**.
- للملفات، افحص الـ MIME الحقيقي والحجم المضبوط وصلاحية الكيان الأب ونتيجة فحص الفيروسات **قبل** ما الملف يبقى متاح. وخزّن برّه الـ web root بأسماء UUID.
- **رسم PDF العميل لازم يستهلك نموذج بيانات آمن للعميل مستحيل يحتوي** على اسم مورد أو سعر مورد أو تكلفة أو هامش أو توفير أو ربح.

## 10. الـ Audit والسجلات والأحداث

- سجلات الـ audit **غير قابلة للتعديل ومحفوظة للأبد**. والعملاء عمرهم ما يكتبوا فيها أو يعدّلوها مباشرة.
- كل تعديل بيسجّل الفاعل والحدث والكيان والقيمة القديمة والجديدة والوقت والـ IP والجهاز و request ID و correlation ID حيث متاح.
- **سجّل دايمًا الأحداث الحرجة الإجبارية:** تعديلات الضريبة/الهامش، وإعادة توزيع العميل، وتغيير الدور، و`Login As`، والاسترجاع من الأرشيف، وتغيير سعر الصرف، وتعطيل الحساب، والموافقة الذاتية.
- أطلق أحداث المجال **بعد** نجاح الـ transaction للتأثيرات العابرة للموديولات، زي إعادة حساب حالة العميل أو تجميع لوحة المعلومات أو فهرسة البحث.
- **الأحداث والمهام لازم تكون idempotent؛** والمستهلكين لازم يتحمّلوا إعادة التسليم من غير بيانات أو إشعارات أو سجلات audit مكررة.
- استخدم سجلات مهيكلة بـ correlation IDs. وسجّل سياق الفشل بأمان؛ **وعمرك ما تسجّل أسرار أو محتوى شخصي/حساس زيادة**.

## 11. الواجهة والتدويل ونظام التصميم

- استخدم توكنز التصميم وقواعد المكوّنات في `Design_System_EN.md`. **متكتبش** ألوان ولا مسافات ولا أنصاف أقطار ولا ظلال ولا اتجاه ولا نصوص للمستخدم في كود الميزات.
- كل النصوص الظاهرة مترجمة من أول يوم. والعربي والإنجليزي لازم يكون معناهم متكافئ؛ والـ RTL/LTR بيتحكم فيه الـ locale، **مش شاشات مكررة**.
- استخدم خصائص التخطيط المنطقية (start/end) بدل افتراضات left/right. وحافظ على ترتيب قراءة الأرقام والتواريخ والعملات والجداول في الـ RTL.
- ابنِ حالات التحميل والفاضي والتحقق والخطأ والمعطّل وممنوع الوصول وانقطاع الاتصال/الـ VPN لكل شاشة حيث ينطبق.
- **متحسبش** الفلوس ولا الصلاحيات ولا انتقالات الحالة ولا قرارات الـ audit في العميل. اعرض نتايج الـ backend واستخدم حالة العميل للعرض/التفاعل الآمن بس.
- حافظ على سلوك كيبورد متاح، وتركيز ظاهر، وتسميات دلالية، وربط الأخطاء، وتباين ألوان في التيمات التلاتة.
- للمبيعات الخارجية، اعمل مسارات مناسبة للمس بأقل كتابة، **واحفظ المسودة عبر انقطاع اتصال قصير من غير ما تقدّم النظام على إنه بيشتغل offline**.

## 12. الطوابير والمهام والـ PDF والـ Adapters الخارجية

- خلّي الطوابير مفصولة بالأولوية الموثّقة: `critical` و `pdf` و `reports` و `maintenance`.
- كل مهمة بتعلن سكيما مدخلاتها واستراتيجية الـ idempotency وحد إعادة المحاولة ومعالجة الفشل وسلوك الـ audit/السجل وحالتها القابلة للملاحظة.
- نفّذ المهام المجدولة J-01 لحد J-14 **بالظبط زي ما هي موثّقة**، بما فيها سلوك الـ catch-up عند التشغيل.
- ولّد الـ PDF بشكل غير متزامن، واستخدم خطوط عربية مضمّنة، وخزّن لقطات ثابتة، وأعد المحاولة عند الفشل، واكشف الجاهزية عبر عقد الـ API.
- حط الـ SMTP والتخزين والبحث والـ PDF وكل تكامل مؤجّل ورا واجهة/adapter. **وانقطاع خدمة خارجية لازم يفشل بأمان من غير ما يوقّف الـ CRM كله.**
- **متضيفش** تكاملات مؤجلة (WhatsApp، Outlook، AI، Mapbox، الإشعارات الفورية) ولا وظائف بعد الـ MVP إلا بقرار معتمد بيوسّع النطاق.

## 13. الاختبار والتحقق

### 13.1 مستويات الاختبار المطلوبة

| المستوى | مطلوب لـ |
|---|---|
| وحدة | قواعد التسعير/الحساب، وسياسات الحالة، والتحقق، وسياسات الصلاحيات، والـ mappers، وكائنات القيمة. |
| تكامل | قيود الداتابيز، والـ migrations، والمستودعات، وصلاحيات الـ API، والـ transactions، وكتابة الـ audit، والطوابير، ومسارات الموديولات. |
| من البداية للنهاية | الدخول، وحدود الأدوار، ودورة حياة العميل/الصفقة/العرض، والموافقة، والـ PDF، وأمر الشراء، والمشتريات، والتسليم، ومسار زيارة الموبايل، والتعافي بعد إعادة التشغيل. |
| أمني/سلبي | كل حد صلاحية، وفشل تحقق، ورفض ملف، وحد معدل، وتحديث عرض متزامن قديم. |

### 13.2 قواعد الاختبار

- **تغيير في الفلوس أو الصلاحيات أو انتقالات الحالة أو النسخ أو أكتر من جدول مالوش استثناء من الاختبار.**
- لإصلاح العيوب، ضيف اختبار انحدار **بيفشل قبل الإصلاح** لما يكون ده ممكن.
- الاختبارات بتستخدم تواريخ ثابتة وقيم `Decimal` وهويات اختبار وأسعار صرف مضبوطة. **وممنوع تعتمد** على الوقت الحالي أو خدمات خارجية أو بيانات إنتاج أو ترتيب التنفيذ.
- **اختبر مسار الدور المسموح والممنوع.** المسار السعيد الناجح **مش بيثبت الصلاحيات**.
- شغّل الفحوص المرتبطة باستمرار أثناء الشغل؛ وقبل التسليم، شغّل مجموعة فحص الأنواع والـ lint والاختبار والبناء والدخان كاملة.

## 14. مراجعة الكود وتعريف الإنجاز

كل تغيير بيبقى جاهز للمراجعة بس لما يجاوب على:

1. أنهي متطلب أو قرار أو قاعدة داتابيز أو مهمة أو معيار قبول موثّق بينفّذه ده؟
2. أنهي أدوار تقدر تقرا وتتصرف في المورد اللي اتغيّر، وإزاي ده مفروض على مستوى الـ API والصف؟
3. أنهي جداول و migrations وقيود وفهارس و transactions وسجلات audit وأحداث اتغيّرت؟
4. أنهي اختبار بيثبت المسار السعيد ومسار الصلاحية السلبي ومسار التحقق/الخطأ ومسار التزامن/النسخ حيث ينطبق؟
5. أنهي حالات ظاهرة للمستخدم موجودة بالعربي والإنجليزي، وفي RTL و LTR، وعبر التيمات حيث ينطبق؟

**متسلّمش الشغل قبل ما:**

- الـ diff يبقى محصور في المهمة ومفيهوش ضوضاء غير مرتبطة.
- الـ migrations تشتغل وترجع نظيف.
- الأنواع والـ lint والاختبارات المرتبطة والبناء وفحوص الدخان تعدّي.
- توثيق الـ API وأي مستند مصدر متأثر يتحدّثوا.
- سجلات الـ audit والصلاحيات والـ pagination والتحقق والتدويل وإتاحة الوصول وآثار الأداء يتفحصوا.
- التسليم يذكر **الأوامر والنتايج الحقيقية** وقائمة اختبار يدوي مختصرة.

## 15. أنماط ممنوعة

- فلوس بـ floating point، أو حسابات مالية بيملكها العميل.
- صلاحيات أو enums شغل أو نصوص للمستخدم أو قيم ثيم أو افتراضات إقليمية مكتوبة في الكود.
- صلاحيات على مستوى الواجهة بس، أو غياب اختبارات الصلاحيات السلبية، أو بيانات اعتماد خدمات متاحة للعميل.
- حذف فعلي، أو تعديل تاريخ audit غير قابل للتغيير، أو تعديل في مكانه لتاريخ نسخ عروض الأسعار/التقارير.
- استعلامات قوائم غير محدودة، أو فلترة في العميل مستخدمة كأمان، أو تصدير من غير pagination بيتخطى الصلاحيات.
- كتابة مباشرة في جداول موديول تاني، أو منطق شغل عام مخفي في helpers، أو تكاملات بتتنادى مباشرة من كود الـ domain.
- حل تعارض في الصمت، أو فقدان مدخلات المستخدم في الصمت، أو الكتابة تلقائيًا فوق عرض سعر قديم.
- ميزات مؤجلة أو تكاملات خارجية أو تغييرات إطار عمل من غير قرار معتمد.
