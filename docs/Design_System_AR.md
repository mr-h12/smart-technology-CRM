# نظام CRM — مواصفة نظام التصميم

> **الحالة:** الأساس التصميمي للتنفيذ.
> **بينطبق على:** الويب على الديسك توب و PWA المبيعات الخارجية، عربي/إنجليزي، RTL/LTR.
> **التوأم:** `Design_System_EN.md` — لازم الاتنين يفضلوا متطابقين دلاليًا.

## 1. الغرض والحدود

نظام التصميم ده بيخلّي الـ CRM متّسق ومتاح وفعّال للشغل اليومي الكثيف بالبيانات. وبينفّذ المتطلب الموثّق بوجود نظام تصميم قبل أول شاشة، ومتطلب المستخدم بوجود **تلات تيمات** قابلة للاختيار.

**دي مواصفة عرض بس.** وعمرها ما تغيّر الصلاحيات ولا سلوك الـ API ولا قواعد الحساب ولا انتقالات الحالة ولا متطلبات الـ audit ولا ظهور المعلومات.

### 1.1 مبادئ التصميم

1. **الوضوح التشغيلي الأول:** الحالة والمالك والعُمر والإجراء المطلوب والتحقق لازم يكونوا سهلين في المسح البصري.
2. **نظام واحد، تلات مظاهر:** المكوّنات وسلوك التفاعل متطابقين عبر التيمات؛ **التوكنز البصرية بس هي اللي بتتغير**.
3. **العربي من الدرجة الأولى:** العربي مش ترجمة لاحقة. والـ RTL والـ LTR تخطيطين مدعومين بالتساوي.
4. **كثيف بس هادي:** شاشات الـ CRM ممكن تعرض كثافة معلومات عالية، بتسلسل هرمي ومساحات بيضا مقصودة.
5. **الإجراءات الآمنة صريحة:** الإجراءات المكافئة للتدمير (الأرشفة، التعطيل، الإرجاع، الرفض) محتاجة تأكيد واضح وحقول سبب حيث مطلوب.

## 2. مكتبة أنماط مستوحاة من Odoo

التيم الأول بيتبنى أنماط تفاعل Odoo CRM، **مش** علامتها التجارية ولا كودها ولا أصولها البصرية. Odoo بيوثّق Kanban للفرص قائم على المراحل، بكروت بتعرض المعلومات الأساسية وبتدعم الحركة بين المراحل؛ وبيفرّق كمان بين عروض القائمة والفورم والبحث والـ Kanban والرسم البياني والـ pivot والتقويم والخريطة. الـ CRM ده بياخد الأنماط اللي تناسب نطاقه الموثّق بس.

### 2.1 أنماط بنتبناها

| النمط | التنفيذ في الـ CRM |
|---|---|
| قشرة تطبيق ثابتة | شريط جانبي قابل للطي للموديولات، على الشمال في LTR وعلى اليمين في RTL. وبيحتوي على الشاشات المسموحة للدور الداخل بس. |
| ترويسة السياق | عنوان الصفحة، ومسار التنقل حيث مفيد، وبحث محدود بالنطاق، وفلاتر، ومبدّل العرض، والإجراء الأساسي المسموح. |
| خط Kanban | كروت الصفقات مجمّعة حسب حالة الصفقة الموثّقة. والكارت بيعرض الكود والعميل والمالك وآخر نشاط والمؤشرات المالية/الحالة المسموحة. **والسحب مسموح بس لما الـ API يصرّح بالانتقال.** |
| قائمة البيانات | جدول بـ pagination من السيرفر، بترتيب أعمدة وفلاتر واختيارات عرض محفوظة حيث موثّق، وعمليات جماعية بس لما الصلاحية تسمح، وحالة فاضية بالإجراء التالي المسموح. |
| فورم السجل | مجموعات حقول واضحة، وحقول محسوبة للقراءة بس، وتحقق داخل الصفحة، ووصول للـ audit/الـ timeline، وسلوك حفظ/إلغاء صريح. |
| مساحة التفاصيل | ترويسة ملخص + تبويبات للـ timeline وعروض الأسعار المرتبطة وعروض الموردين والمستندات/المرفقات والإجراءات المسموحة للدور. |

### 2.2 أنماط بنرفض ننقلها

- **متضيفش** أنشطة Odoo ولا المتابعات التلقائية ولا استقبال البريد ولا التسويق ولا الدردشة ولا التكاملات الخارجية: دي مؤجلة أو برّه نطاق الـ MVP.
- **متدخّلش** عروض مش مدعومة للدور أو الموديول المعني لمجرد إن Odoo بيوفرها.
- **متحصرش** الـ CRM في تنفيذ Kanban البصري بتاع Odoo. نموذج حالات الصفقة الموثّق هو المرجع؛ والمراحل النهائية ممكن تتطوى واللوحة ممكن تتمرر أفقيًا أو تستخدم منتقي مراحل على الشاشات الصغيرة.
- **عمرك ما تسمح** لتفاعل سحب وإفلات بصري إنه يتخطى صلاحية الـ API أو تحقق انتقال الحالة.

## 3. معمارية التيمات

### 3.1 سلوك التيم القابل للاختيار

- التيمات التلاتة هي: **Odoo-inspired** و **Clean White** و **Dark Blue**.
- اختيار التيم تفضيل عرض لكل مستخدم، محفوظ في ملفه؛ وقبل الدخول، الافتراضي هو **Odoo-inspired**.
- تغيير التيم بيحدّث توكنز اللون والحدود والظل والتركيز بس. **وما بيصفّرش** اللغة ولا الاتجاه ولا الفلاتر ولا الصلاحيات ولا البيانات.
- التيم المختار لازم يتطبّق **قبل** ما قشرة التطبيق ترسم، علشان ميحصلش وميض لتيم تاني.
- لغة النظام بتتحكم في الاتجاه بشكل مستقل: العربي = RTL، الإنجليزي = LTR.
- كل تيم لازم يحقق تباين **WCAG 2.1 AA** للنص العادي وعناصر التحكم.

### 3.2 عقد التوكنز الدلالية

المكوّنات بتستهلك توكنز دلالية بس. **متستخدمش قيم hex بتاعة التيم مباشرة في المكوّنات.**

```css
--color-canvas; --color-surface; --color-surface-raised; --color-surface-muted;
--color-text; --color-text-muted; --color-text-inverse; --color-border;
--color-primary; --color-primary-hover; --color-primary-active; --color-primary-text;
--color-focus-ring; --color-link;
--color-success; --color-warning; --color-danger; --color-info;
--color-status-neutral; --shadow-1; --shadow-2;
```

## 4. الأساسيات

### 4.1 الخطوط

| السياق | العربي | الإنجليزي / الأرقام | الوزن والاستخدام |
|---|---|---|---|
| واجهة sans | Noto Sans Arabic | Inter | 400 للنص؛ 500 للتسميات؛ 600 للعناوين/الإجراءات؛ 700 للإجماليات الأساسية بس |
| Monospace | Noto Sans Mono | Noto Sans Mono | الأكواد والمعرّفات وبيانات الـ audit بس |

- حجم النص الأساسي: `14px / 1.55`؛ نص الجداول المضغوط: `13px / 1.45`.
- عنوان الصفحة: `24px / 1.3 / 600`؛ عنوان القسم: `18px / 1.35 / 600`؛ عنوان الكارت: `16px / 1.4 / 600`.
- **استخدم أرقام جدولية** للفلوس والأعداد والأكواد والتواريخ. **ومتعكسش ترتيب الأرقام في الـ RTL.**
- **عمرك ما تستخدم اللون لوحده** لحالة أو وضع مطلوب.

### 4.2 المسافات والشكل والارتفاع

| التوكن | القيمة | الاستخدام الأساسي |
|---|---:|---|
| `space-1` | 4px | فراغ الأيقونات والمسافات الداخلية المضغوطة |
| `space-2` | 8px | المسافة بين الحقول وعناصر التحكم |
| `space-3` | 12px | داخل الكروت وحشو خلايا الجداول |
| `space-4` | 16px | الحشو القياسي للمكوّنات |
| `space-5` | 20px | مجموعات الفورم |
| `space-6` | 24px | المسافة بين الأقسام |
| `space-8` | 32px | أقسام الصفحة الرئيسية |
| `space-10` | 40px | الفصل على الشاشات الكبيرة |

- نصف القطر: `6px` لعناصر التحكم، `8px` للكروت، `12px` للحوارات؛ **متستخدمش** أشكال دائرية كاملة إلا للشارات والشرائح.
- `shadow-1`: ارتفاع خفيف للكارت/القائمة في وضع السكون؛ `shadow-2`: للحوارات والـ popovers بس.
- أقصى عرض للمحتوى على الديسك توب: `1600px`؛ وقشرة التطبيق بتفضل بعرض كامل لجداول البيانات.

### 4.3 التخطيط المتجاوب

| نقطة الكسر | سلوك التخطيط |
|---|---|
| `< 640px` | موبايل أولًا للميدان؛ عمود محتوى واحد؛ الشريط الجانبي بيبقى drawer؛ الجداول بتبقى كروت أو تتمرر أفقيًا عند الضرورة بس. |
| `640–1023px` | فورمات بعمودين لما الحقول تكون قصيرة؛ وأدوات فلترة مضغوطة. |
| `≥ 1024px` | شريط جانبي ثابت قابل للطي؛ وفورمات متعددة الأعمدة؛ وجداول كاملة وعروض مقسّمة. |

## 5. قشرة التطبيق والتنقل

### 5.1 هيكل القشرة

```text
LTR: [الشريط الجانبي] [شريط السياق العلوي] [محتوى الصفحة]
RTL: [محتوى الصفحة] [شريط السياق العلوي] [الشريط الجانبي]
```

- عرض الشريط الجانبي: `256px` مفتوح، `72px` مطوي. **استخدم خصائص CSS المنطقية، مش تموضع left/right.**
- جمّع التنقل حسب موديول الشغل. واعرض شارة لعدّادات الـ MVP بس: الطلبات، الموافقات، التقارير، وعروضي.
- **متعرضش** موديول ولا إجراء ولا عدّاد ولا رابط سجل الدور مش مسموح له بالوصول ليه.
- شريط السياق العلوي فيه عنوان الصفحة ومسار تنقل اختياري وأدوات بحث/فلترة محدودة بالدور ومبدّل عرض واللغة وتفضيل التيم وقائمة المستخدم.

### 5.2 العروض

| العرض | الاستخدام | المتطلبات |
|---|---|---|
| Kanban | الصفقات، وعروض الأسعار لما مسح الحالات يكون مفيد، والزيارات حيث مناسب. | أعمدة حالات، وعدّاد، وطي المراحل النهائية، وحركة مصرّح بيها من الـ API بس، **وبديل متاح من غير سحب**. |
| جدول/قائمة | العملاء، الموردين، التقارير، عروض الأسعار، والسجلات الكثيفة وعالية الحجم. | pagination، وفلاتر/ترتيب/بحث من السيرفر، وأولويات أعمدة، وحالات فاضي/تحميل/خطأ. |
| تفاصيل | عميل أو صفقة أو عرض أو عرض مورد أو تقرير أو زيارة واحدة. | الملخص أولًا، والبيانات المرتبطة/الـ timeline ثانيًا، وأزرار الإجراءات بالصلاحية بس. |
| فورم/باني | إنشاء/تعديل عميل أو صفقة أو عرض مورد أو عرض سعر أو زيارة أو تقرير. | أقسام واضحة، وعلامات إجبارية، وتحقق داخل الصفحة، وقيم محسوبة للقراءة بس، وتحذير من التغييرات غير المحفوظة. |
| لوحة معلومات | Manager، Team Leader، CEO، Super Admin. | مقاييس خاصة بالدور، وفلتر زمني، ورسوم متاحة، **ومفيش drill-down للـ CEO**. |

## 6. مواصفات المكوّنات

### 6.1 متطلبات التفاعل المشتركة

- كل عنصر تفاعلي له تركيز كيبورد ظاهر باستخدام `focus-ring`.
- الأزرار والمدخلات متاحة بالكيبورد؛ و Enter بينشّط الإجراء الأساسي **لما يكون آمن بس**؛ و Escape بيقفل الحوارات/القوائم **من غير تجاهل صامت**.
- استخدم أيقونات start/end منطقية علشان تنعكس صح في الـ RTL؛ **ومتعكسش** الرموز المفهومة عالميًا زي علامة الزائد أو الصح أو التنبيه.
- عناصر التحكم أثناء التحميل بتحافظ على عرضها وبتعرض بديل نصي. والعناصر المعطّلة بتشرح السبب لما ميكونش واضح.
- اعرض تحقق السيرفر جنب الحقل المعني **واحتفظ بالقيم المدخلة عند فشل التحقق**.

### 6.2 الأزرار والإجراءات

| النوع | الاستخدام | الاستخدام الممنوع |
|---|---|---|
| Primary | إجراء أساسي واحد مسموح في السياق: حفظ، إرسال للموافقة، إنشاء. | أكتر من إجراء أساسي متنافس في قسم واحد. |
| Secondary | إجراءات مساندة: معاينة، إضافة بند، تحديث الأسعار. | العمليات التدميرية. |
| Ghost | إجراءات منخفضة الأهمية في الجداول/الكروت. | تأكيد مسار شغل حرج. |
| Danger | أرشفة، تعطيل، رفض، أو إجراء مكافئ لغير القابل للتراجع. | الحفظ العادي أو الإرسال أو تقدّم الحالة. |

كل أنواع الأزرار ليها حالات: افتراضي، hover، نشط، تركيز، معطّل، وتحميل.

### 6.3 عناصر الفورم

| المكوّن | المعيار |
|---|---|
| مدخل نصي | تسمية فوق، ونص مساعدة اختياري، وعلامة إجباري صريحة، وخطأ داخل الصفحة، وعدّاد/حد أقصى حيث ينطبق. |
| قائمة/combobox | بحث لما حجم الخيارات يستدعي؛ وعرض تحذير الاختيار المعطّل لما الـ CRM يسمح باستخدامه. |
| حقل عملة | خلّي المبلغ والعملة مقترنين بصريًا؛ واستخدم قواعد الإدخال العشري؛ والتنسيق للعرض بس؛ والإجماليات المحسوبة للقراءة بس. |
| حقل تاريخ | عرض حسب الـ locale، وقيمة آمنة بـ ISO، ودعم كيبورد للتقويم، وتحقق أيام العمل حيث ينطبق. |
| مدخل شروط ذكي | نص حر باقتراحات قابلة لإعادة الاستخدام؛ **والاقتراحات عمرها ما تفرض جدول دفع مهيكل**. |
| رفع ملف | بيعرض الصيغ المسموحة وحد الحجم المضبوط وحالة الرفع/الفحص ومتطلب صلاحية الكيان الأب. |

### 6.4 نظام الحالات والشارات والتنبيهات

| النوع | المعنى | العرض |
|---|---|---|
| نجاح | معتمد، مقبول، مكسوب، تم التسليم. | أيقونة خضرا + نص/شريحة؛ **عمره ما يكون لون بس**. |
| تحذير | معلّق، راكد، عرض منتهي، صنف معطّل مختار، موافقة ذاتية. | أيقونة كهرمانية + تسمية؛ والموافقة الذاتية ليها **شارة صفرا**. |
| خطر | مرفوض، خسران، منع تحقق، مهمة فاشلة. | أيقونة حمرا + تسمية؛ والسبب/الإجراء المطلوب واضح. |
| معلومة | مسودة، مسند، إرشاد محايد. | أيقونة زرقا/محايدة + تسمية. |

استخدم ألوان تقييم الموردين الموثّقة (أخضر، أصفر، أحمر، أبيض) **كشرائح تقييم موردين بس**؛ **متعيدش استخدامها** لحالات عامة.

### 6.5 الجداول وكروت الـ Kanban

- الجداول بتستخدم ترويسة ثابتة في القوائم الطويلة، وارتفاع صفوف مقروء، ومحاذاة أعمدة حسب نوع البيانات، وحالة تركيز/اختيار واضحة للصف.
- **حاذِ القيم المالية على الشمال واستخدم أرقام جدولية**؛ واستخدم المحاذاة المنطقية للحفاظ على ترتيب القراءة الصحيح في الـ RTL.
- **كل قائمة بـ pagination من السيرفر. متعملش واجهة بتتطلب تحميل كل السجلات.**
- كروت الـ Kanban بتعرض الحقول اللازمة لاتخاذ الإجراء التالي بس. والمعلومات الكاملة مكانها التفاصيل.
- **كل عمليات السحب ليها إجراء "نقل" متاح بالكيبورد** بقائمة مراحل مصرّح بيها من الـ API.

### 6.6 الحوارات والتأكيدات والـ toasts

- الحوارات بتحبس التركيز، وبتسمّي غرضها، وبتدعم Escape حيث الإلغاء آمن، وبترجّع التركيز للعنصر اللي فتحها.
- إجراءات الأرشفة والتعطيل والرفض والإرجاع والموافقة بتعرض نتيجتها **وبتجمع الأسباب/الملاحظات الإجبارية قبل الإرسال** حيث مطلوب.
- استخدم التحقق داخل الصفحة لأخطاء الفورم المتوقعة. واستخدم الـ toast لتغذية راجعة مختصرة للإتمام/الفشل بس؛ **والـ toast ممنوع يكون المكان الوحيد اللي الخطأ متشرح فيه**.

## 7. أنماط خاصة بالـ CRM

### 7.1 خط الصفقات

- اعرض الحالات الموثّقة بس: `Lead` و `Contacted` و `Waiting Customer Request` و `Supplier RFQ` و `Supplier Quotation` و `Quotation Sent` و `Negotiations` و `Won` و `Purchasing` و `Delivery` و `Delivery Complete` و `Lost`.
- خلّي أعمدة الحالات النهائية متميزة بصريًا وقابلة للطي. والمستخدم يقدر يفتحها من غير ما يفقد بيانات.
- **كل كارت لازم يوفّر مسار إجراء لتغيير الحالة من غير سحب.** والسيرفر هو اللي بيقرر الصلاحية والانتقال المسموح.
- اعرض حالة ركود الصفقة وآخر نشاط حيث الدور مسموح له يشوف الصفقة.

### 7.2 باني عرض السعر والموافقة

- خلّي اختيار المورد والتكلفة الداخلية والهامش وسعر العميل والخصم والضريبة والبنود الإضافية والإجمالي النهائي في **مجموعات بصرية منفصلة**.
- علّم القيم المحسوبة من الـ backend **وامنع تعديلها مباشرة** حيث القاعدة الموثّقة بتتطلب الحساب.
- **فرّق بين التحذير والمنع:** سعر المورد الناقص **بيمنع الحفظ**؛ والكمية الأعلى من المتاح المسجّل **بتعرض تحذير أحمر داخل السطر من غير منع**.
- تغيّر سعر المورد في `Draft`/`Pending` والأصناف المعطّلة في العروض المفتوحة بتعرض التحذير الموثّق + الإجراء المسموح.
- **معاينة ومخرج PDF العميل لازم يستبعدوا أسماء الموردين وأسعارهم والتكاليف والهوامش بشكل مطلق.**
- العرض المعتمد ذاتيًا بيعرض **الشارة الصفرا الموثّقة** في كل شاشة موافقة/تقرير معنية.

### 7.3 فورم الزيارة الخارجية

- موبايل أولًا؛ **والحقول الإجبارية الوحيدة هي: اسم الشركة، والشخص المسؤول، والنتيجة**.
- استخدم عناصر بسيطة للنعم/لأ ومربعات الاختيار والقوائم. وخلّي النص الحر الاختياري مقصود.
- **اعرض حالة انقطاع VPN محددة واحتفظ بمسودة الفورم أثناء انقطاع قصير.**
- النتايج بنص واضح + أيقونة: **مرفوض** محتاج سبب، و**مفتوح** بيحتفظ بتاريخ متابعة، و**ناجح** بيعرض حالة التسليم.

## 8. إتاحة الوصول وبوابات الجودة

قبل ما المكوّن أو الشاشة تخلص، تأكد من:

- تباين **WCAG 2.1 AA** للنص وعناصر التحكم **في التيمات التلاتة**.
- مسار كيبورد كامل، وتركيز ظاهر، ومفيش حبس كيبورد برّه الحوارات.
- عناوين دلالية، وتسميات، وربط الأخطاء، وإعلان تغيّر الحالة، وتسميات أيقونات ذات معنى.
- ترتيب بصري صحيح في الـ RTL، وسلوك المؤشر، وعلامات الترقيم، والجداول، والأرقام، والرسوم، والتموضع المنطقي start/end.
- **مساحات لمس `44 × 44px` على الأقل** للإجراءات الأساسية على الموبايل.
- حالات التحميل والفاضي والخطأ والمعطّل وممنوع الوصول.
- **مفيش مكوّن بيكتب لون أو نصف قطر أو مسافة أو ظل أو اتجاه بيتخطى التوكنز.**

## 9. معايير قبول التنفيذ

1. لأي مستخدم مسجّل، لما يختار واحد من التيمات التلاتة، التفضيل بيتحفظ لحسابه وبيتطبّق في الجلسة الجاية.
2. سواء عربي أو إنجليزي، لما المستخدم يغيّر التيم، اللغة والاتجاه **ما بيتغيروش**.
3. لإجراء مقيّد بدور، لما المستخدم يشوف أي تيم، الإجراء بيفضل مخفي أو معطّل **كمكمّل بصري لفرض الـ API بس**.
4. للوحة Kanban الصفقات، لما المستخدم ميقدرش يسحب أو بيستخدم الكيبورد، بيقدر يستخدم إجراء تغيير حالة متاح **بنفس تحقق الـ API**.
5. لأي مكوّن في أي تيم، لما يدخل حالة تركيز أو خطأ أو تحميل أو تعطيل، الحالة **ظاهرة من غير الاعتماد على اللون وحده**.
6. لملف PDF عرض سعر للعميل، لما يتولّد من أي تيم، محتوى الـ PDF بيفضل **مستقل عن التيم وبيستبعد كل بيانات الموردين/التكلفة/الهامش**.
